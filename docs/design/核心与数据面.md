# 设计文档：会话绝对过期、SQLite 连接复用与启动完整性检查、数据面过滤与聚合

> 功能项：`session-expiry`（token 绝对过期）、`sqlite-conn-reuse`（SQLite 连接复用、批量提交与启动 integrity_check）、`data-plane-filters`（死区过滤、变化上报、滑动窗口聚合）。
> 本文自包含：实现者只需读本文与文中引用的源码文件，无需其他评审材料。所有路径均相对仓库根目录，行号以撰写时的 `main` 分支（commit 17da7cd）为准。

---

## 一、目标与范围

| 功能项 | 目标 | 主要改动面 |
|---|---|---|
| `session-expiry` | 用户登录 token 增加**绝对过期时间**（自签发起算，不因活动续期）；过期后所有携带该 token 的请求返回 401，前端自动登出 | `gateway/gateway-server/src/users/store.rs`、`gateway/gateway-server/src/config.rs`、`gateway/gateway-server/src/api/handlers.rs` |
| `sqlite-conn-reuse` | `data.db` 的读写改为**进程内共享的单个长连接**（互斥复用），消除"每次操作新开连接 + 重设 PRAGMA + 重建 schema"的开销；启动时对 `data.db` 执行 `PRAGMA integrity_check`，损坏时自动从 `data.db.bak` 恢复 | `gateway/gateway-core/src/persist.rs`、`gateway/gateway-server/src/users/store.rs`、`gateway/gateway-server/src/main.rs` |
| `data-plane-filters` | 在采集 → 总线的数据链路上支持组级**死区过滤 / 变化上报（含心跳）**与**滑动窗口聚合**，配置挂在组维度，规则引擎语义不受影响 | `gateway/gateway-core/src/filters.rs`（新增）、`gateway/gateway-core/src/manager.rs`、`gateway/gateway-core/src/store.rs`、`gateway/gateway-core/src/persist.rs`、`gateway/gateway-core/src/data_flow.rs`、`gateway/gateway-server/src/api/*` |

**不在范围内**（明确排除，防止实现走偏）：

- 不做 JWT / OAuth，不引入刷新 token 与滑动续期（绝对过期的语义就是"从登录起算，到点失效"）。
- 不做 SQLite 连接池（r2d2 等）与多连接并发写；不做 `history.db` 的 integrity_check（它是独立文件，写线程本就持长连接，见 `gateway/gateway-server/src/history.rs:243-256, 264`）。
- 数据面过滤不改动 `gateway-sdk` 的 trait、FFI ABI 与 `GroupData` 结构（见 §4.3）；不新增独立采集任务。
- 不做多租户（形态 B 的 `tenant_id` 改造见 `docs/多租户决策方案.md`，与本三项正交；`session-expiry` 的会话模型未来可自然扩展 `tenant_id` 字段，无需返工）。

## 二、现状与衔接点

### 2.1 会话与认证现状

- 用户 token 是登录时生成的 `Uuid::new_v4()`，存于 `users` 表 `token` 列（`gateway/gateway-server/src/users/store.rs:15-27`、`store.rs:333-338`），**没有任何过期字段**；每个用户同时只有一个有效 token（新登录会顶掉旧 token，`store.rs:346-354`）。
- 内存缓存 `tokens: RwLock<HashMap<String, UserRole>>`（`store.rs:134`）是鉴权的**权威口径**：`role_of(token)`（`store.rs:399-404`，用 `try_read` 非阻塞读）被认证中间件调用（`gateway/gateway-server/src/api/mod.rs:155`）；启动时把 DB 中所有非空 token 灌进该缓存（`store.rs:225-234`）。
- 登出（`store.rs:377-396`）与改密（`store.rs:587-626`）已实现失效；登录失败 5 次锁 5 分钟已实现（`store.rs:32-34, 273-288`）。`docs/功能实现清单.md` 第七节也明确："token 过期与改密失效已完成（**绝对过期时间仍待 B2**）"——本项就是补上这最后一块。
- 两条**无过期**的旁路，设计上保持不变：
  1. 静态 token `GATEWAY_TOKEN`：认证中间件里恒定时间比较、视为 Admin（`api/mod.rs:143-152`）。它是机器级 API 密钥，不是用户会话。
  2. 遗留登录：用户库为空时 `admin + config.token` 直接换发静态 token（`api/handlers.rs:112-126`）。
- 前端已具备 401 处理：`web/src/api.js:86` 收到 401 调 `handleUnauthorized()`（`api.js:48-60`），清除本地 token 并跳转 `#/login`。**后端返回 401 即等于前端自动登出，前端无需改动。**

### 2.2 SQLite 持久化现状

`data.db` 一套库同时承载**配置快照**（nodes/groups/tags/subscriptions/rules）与**用户表**（`main.rs:138` 取 `config.data_db()`，`main.rs:154` 加载快照、`main.rs:198` `UserStore::open(&db_path)` 用同一路径），但两处代码各自为政：

- **配置快照**（`gateway/gateway-core/src/persist.rs`）：每次 `load_secret`（`persist.rs:734-738`）和 `save_secret`（`persist.rs:762-774`）都新开一个 `Connection`，随后每次都执行 `apply_pragmas`（WAL/synchronous/busy_timeout/foreign_keys，`persist.rs:180-187`）与 `ensure_schema`（`persist.rs:163-173`）。保存本身已是**单事务批量提交**（`save_to_db`，`persist.rs:568-722`：UPSERT + 临时键表差集删除 + `prepare_cached`），上层还有 300ms 写合并去抖（`state.rs:67-79`、`main.rs:244-257`，`GATEWAY_PERSIST_DEBOUNCE_MS=0` 可关）。
- **用户存储**（`gateway/gateway-server/src/users/store.rs`）：`open/login/logout/list/get/create/update_simple/delete/set_password/has_any_user` 共 **10 处**调用点（`store.rs:185, 293, 385, 412, 444, 489, 523, 563, 603, 634`）每次操作都新开连接、各写各的事务。与快照写入并存时互不知晓，且**两侧不对称**：只有快照侧连接经 `apply_pragmas` 设了 `busy_timeout=5000`（`persist.rs:180-187`），users 侧全部连接未设任何 PRAGMA，`busy_timeout` 为默认 0——冲突时 users 操作**立即收到 SQLITE_BUSY 失败**而非等锁。这一不对称正是单连接方案最有力的动机。
- **备份**：`maybe_backup` 以每小时节流执行 `VACUUM INTO data.db.bak`（`persist.rs:782-823`），产出事务一致快照——这是 integrity_check 失败后的现成恢复源。
- **历史库** `history.db` 是独立文件，写线程已持单个长连接并批量事务（`gateway/gateway-server/src/history.rs:258-341`），查询路径按次开只读连接（`gateway/gateway-server/src/history.rs:427, 465, 499`，频率低，不动）。
- 全仓库 `Connection::open` 调用点已枚举核对（本次 `grep -rn "Connection::open"` 实测），除上述外仅剩测试代码。
- **当前不存在任何 integrity_check / quick_check 调用**（本次 grep 验证为空）；加载失败仅打 warn 并以空配置继续（`main.rs:177`），库损坏时会静默丢失全部配置。

### 2.3 数据面现状（第 3 项的关键衔接）

数据链路：南向 `poll_group` → `poll_group_once`（`gateway/gateway-core/src/manager.rs:1121-1236`，每个运行中南向节点的调度任务按组固定节拍调用）→ 成功分支内依次：

1. **规则求值**：`rules::evaluate_and_fire(store, plugin, id, gid, &values)`（`manager.rs:1160-1170`），无启用规则时立即返回（`rules.rs:304-315`）；规则按 `(south_node, group)` 命中（`store.rs:250-258`）。
2. **最近值缓存**：`last_values.insert((id, tid), LastValue{...})`（`manager.rs:1172-1182`），供 `GET /api/nodes/:id/values` 只读展示。
3. **GroupData 构造与发布**：`tag_names` 从 Store 逐点查名（`manager.rs:1184-1194`），`bus.publish`（分区广播 + 旁路 tap，`bus.rs:62-75`），点位级指标 `record_south_published_tags`（`manager.rs:1204`）。

可直接复用的机制（第 3 项全部沿用这些先例，不发明新轮子）：

- **规则引擎的配置-状态分离**：规则是纯配置进快照持久化（`persist.rs:97-98` 的 `#[serde(default)] rules`、`persist.rs:420-461` 读写、`persist.rs:685-718` UPSERT），运行期状态放在进程级引擎（`rules.rs:202-282`，`DashMap`），删除时 `forget`（`manager.rs:196-203`）。
- **规则 API 先例**：`/api/rules` CRUD（`api/mod.rs:213-218`），写操作要求 Admin（`api/mod.rs:75-78`），创建时校验引用存在性（`handlers.rs:2050` `validate_rule_refs`），落盘 `state.persist().await`（`handlers.rs:2052`）。
- **旁路消费者**：`Bus::subscribe_all`（`bus.rs:82-89`）被历史落库使用（`gateway/gateway-server/src/history.rs:147-171`）——过滤发生在 publish 之前意味着**历史库记录的是上报口径的数据**，本文将其明确为设计语义（§4.4）。
- **GroupData 自带 `tag_names: Option<HashMap<TagId, String>>`**（`gateway/gateway-sdk/src/messages.rs:9-24`）：北向插件与历史库都以点位名为 key，这为"窗口聚合输出虚拟点位"提供了现成通道，不需要动 SDK。
- **资源删除时的状态清理先例**：`node_remove` 清 bus 分区、点位指标、最近值缓存（`manager.rs:293-299`）；`group_remove` 同理（`manager.rs:700-712`）。
- **指标体系**：`DataFlowMetrics` 原子计数 + 快照（`data_flow.rs:29-69, 159-185`），经 `/api/data-flow`（`api/mod.rs:209`）与 `/api/metrics` 暴露。
- 轮询周期下限 `MIN_POLL_INTERVAL_MS = 10`（`manager.rs:43`）；`Tag`（`gateway/gateway-sdk/src/types.rs:211-222`）无任何过滤字段——本设计**不改 Tag 结构**，死区等配置挂在组级策略对象上（§4.3）。

## 三、方案

### 3.1 依赖选型及理由（已实际核实）

本设计**不引入任何新 crate**，三项功能全部用工作区既有依赖实现。核实过程（2026-10-05 执行）：

| crate | 核实命令与结果 | 结论 |
|---|---|---|
| `rusqlite 0.31`（bundled） | `grep Cargo.lock` → `version = "0.31.0"`；`cargo info rusqlite@0.31` → `version: 0.31.0 (latest 0.40.2)` | 继续用 0.31，**不在本次升级**（升级到 0.40 涉及 API 变更面，与三项功能无关，单独排期）。`PRAGMA integrity_check` 是 SQLite 内置命令，bundled 版本直接可用，经 `Connection::query_row("PRAGMA integrity_check", ...)` 读取结果行 |
| `r2d2 0.8.10` / `r2d2_sqlite 0.35.0` | `cargo info r2d2`、`cargo info r2d2_sqlite` → 均存在可下载 | **存在但拒绝采用**：本仓库对 `data.db` 是"单进程、写已串行（去抖合并 + 单事务）、读多写少"的负载，一个 `Mutex<Connection>` 就够；引入两个新依赖 + 版本配对问题（r2d2_sqlite 当前主线面向更新版 rusqlite）只增加复杂度 |
| 会话过期 | 无需新依赖：时间用 `std::time::SystemTime`（`users/store.rs:47-52` 已有 `now_secs()`），过期判定是纯比较 | — |
| 数据面过滤 | 无需新依赖：并发容器用既有 `dashmap 5`，时间用 `std::time::Instant`（仿 `rules.rs:290-296` 的单调毫秒），浮点聚合手写，虚拟点位 id 用既有 `uuid v4` | — |

`uuid` 已带 `v4` feature（`gateway/gateway-core/Cargo.toml`、`gateway/gateway-server/Cargo.toml`），不新增 `v5` feature。

### 3.2 功能项一：`session-expiry`（token 绝对过期）

#### 配置项

| 配置 | 位置 | 默认 | 说明 |
|---|---|---|---|
| `GATEWAY_SESSION_TTL_SECS` | 环境变量 > `config/gateway.json`（`ConfigFile.session_ttl_secs`，`#[serde(default = "default_session_ttl_secs")]`）> 默认 | `43200`（12 小时） | 会话绝对过期秒数；`0` 表示永不过期（完全恢复现状）。加入 `Config` 结构体（`config.rs:10-61`）与 `from_env()`（`config.rs:274-411`），并同步补进 `ensure_default_config_file` 写出的默认文件（`config.rs:244-270`）与 `from_file`（`config.rs:207-241`，注意 `from_file` 现在会硬编码非默认字段，新字段必须同样带上） |

#### 数据结构

- `users` 表加列（`store.rs:15-27` 的 `USERS_SCHEMA` 追加列无法作用于已存在的表，需显式迁移）：

  ```sql
  ALTER TABLE users ADD COLUMN token_expiry INTEGER;  -- UNIX 秒；NULL = 未记录（升级前签发的旧 token）
  ```

  迁移方式：`UserStore::open` 在 `execute_batch(USERS_SCHEMA)` 后尝试执行该 ALTER，捕获 "duplicate column name" 类错误并忽略（rusqlite 返回 `Error::SqliteFailure`，按 `ErrorCode::ColumnNameNotFound`/消息匹配跳过；实现时以"执行失败即视为列已存在"处理，不做脆弱的字符串精确匹配，但要在 warn 日志里带上原始错误以便排障）。
- 内存会话条目升级（`store.rs:134`）：

  ```rust
  pub struct Session {
      pub role: UserRole,
      /// 绝对过期时刻（UNIX 秒）；None = 永不过期（仅 ttl=0 时出现）
      pub expires_at: Option<i64>,
  }
  tokens: RwLock<HashMap<String, Session>>,
  ```

- `UserStore` 增加 `session_ttl_secs: u64` 字段，由 `UserStore::open(db_path, session_ttl_secs)` 传入（调用点 `main.rs:198` 改为 `UserStore::open(&db_path, config.session_ttl_secs)`）。为不破坏既有测试（`api/mod.rs:554` 等直接 `UserStore::open(&dir.join("data.db"))`），提供带默认值的包装或改测试传 `0`——**推荐直接改测试调用点**（仅 `api/mod.rs` 测试与 `handlers` 相关测试），避免出现两个语义不同的构造函数。

#### 行为

1. **签发**：`login` 成功时 `expires_at = (ttl == 0) ? None : Some(now_secs() + ttl)`；同时写 DB（`UPDATE users SET token = ?1, token_expiry = ?2`，替换 `store.rs:335-338`）与内存（`store.rs:348-354` 处构造 `Session`）。登录响应体追加过期时刻（`handlers.rs:94-103`）：`"expires_at": <unix 秒或 null>`，前端可展示但非必需。
2. **校验**：`role_of(token)`（`store.rs:399-404`）改为：取 `Session` 后，若 `expires_at` 存在且 `now_secs() >= expires_at` → 返回 `None`（中间件按未知 token 处理返回 401，`api/mod.rs:174-199` 不需要任何改动——这是把改动收敛在 UserStore 内的关键）。`role_of` 仍保持同步 `try_read`，**过期条目不在此处删除**（需要写锁；条目数 = 用户数，每用户单 token，永不增长，惰性清理即可）。
3. **启动加载**：`open` 时灌内存的查询（`store.rs:225-234`）改为：
   - `ttl == 0`：与现状一致，全部加载、`expires_at = None`；
   - `ttl > 0`：只加载 `token_expiry NOT NULL AND token_expiry > now` 的行，且内存 `expires_at` 直接沿用 DB 值（不是"再加一次 ttl"）；`token_expiry IS NULL` 的行（升级前签发的旧 token）**视为已过期、不加载**——升级后存量会话一次性强制重登录，安全优先。
4. **惰性清理**：`login` 现有逻辑本就会移除该用户的旧 token（`store.rs:346-354`），过期 token 因此在用户下次登录时自然清出内存；DB 行由新登录的 UPDATE 覆盖。不引入后台清扫任务。
5. **登出 / 改密 / 删除用户**：不变（已有路径清内存 + 置空 DB token；DB 里同时把 `token_expiry` 置 NULL，保持一致）。
6. **静态 token 与遗留登录**：不经过 `Session`，永不过期，行为不变（§2.1 两条旁路）。

#### 接口形状变化

`POST /api/auth/login` 响应由 `{token, user}` 变为 `{token, expires_at, user}`（新增字段向后兼容）。其余接口无契约变化（401 语义与现状完全一致）。

### 3.3 功能项二：`sqlite-conn-reuse`（连接复用、批量提交、integrity_check）

#### 核心抽象：`persist::Db`

在 `gateway/gateway-core/src/persist.rs` 内新增（或拆出 `gateway/gateway-core/src/persist_db.rs` 并在 `lib.rs` 导出）：

```rust
/// data.db 的进程内共享连接：单连接 + 互斥，全部 SQLite 访问经 with() 串行执行。
pub struct Db {
    conn: std::sync::Mutex<rusqlite::Connection>,
}

impl Db {
    /// 打开（或修复后打开）库文件：integrity_check 门禁 → PRAGMA → ensure_schema，各只做一次。
    pub fn open(path: &Path, integrity: IntegrityMode) -> Result<Arc<Db>, PersistError>;
    /// 在连接上执行一段同步 SQLite 操作（内部 spawn_blocking 由调用方负责）。
    pub fn with<T>(&self, f: impl FnOnce(&rusqlite::Connection) -> Result<T, PersistError>)
        -> Result<T, PersistError>;
}

pub enum IntegrityMode { Full, Quick, Off }   // GATEWAY_DB_INTEGRITY=full|quick|off，默认 full
```

要点：

- `rusqlite::Connection` 是 `Send` 非 `Sync`，`Mutex` 包裹后满足跨任务共享；所有既有调用已运行在 `spawn_blocking` 里（`persist.rs:734, 762`、`users/store.rs` 各处），持锁阻塞的是 blocking 线程池而非 tokio worker，语义安全。写负载已被去抖合并为 ≥300ms 一次、users 操作为低频短事务，单连接串行不会成为瓶颈——这是拒绝连接池的量化依据。
- `load_secret` / `save_secret` 重构为 `Db` 方法（`db.load_snapshot(secret)` / `db.save_snapshot(secret, &snap)`）：删除其中的 `Connection::open*`、`ensure_schema`、`apply_pragmas` 调用（这些全部前移到 `Db::open` 一次完成）；`save_to_db` / `load_from_db` / `maybe_backup` 本体不动（它们只依赖 `&Connection`）。`maybe_backup` 挂在 `save_snapshot` 内部，节流行为保持（`persist.rs:782-823`）。
- **既有自由函数 `save` / `load` 保留为兼容包装**：内部"临时开连接 + 调 `save_to_db`/`load_from_db`"，供现有测试（`persist.rs:899-1158`）与外部路径继续使用。生产启动路径一律走 `Db`。
- `AppConfig` 层：`AppState` 增加字段 `db: Option<Arc<persist::Db>>`（`gateway/gateway-server/src/state.rs:13-27`；`None` 兼容测试环境），`flush()`（`state.rs:83-95`）改调 `db.save_snapshot`；`main.rs` 在创建数据目录后（`main.rs:135-137`）、加载快照前（`main.rs:154`）执行 `Db::open`，并把同一个 `Arc<Db>` 传给 `persist` 加载与 `UserStore::open`（用户表与配置快照共用一库，从此只有一个连接，`busy_timeout` 相关的跨连接等锁场景消失）。

#### 启动 integrity_check 与自动恢复

`Db::open` 内执行（`IntegrityMode::Off` 整体跳过检查）。**顺序与分类是硬性要求**（SQLite 默认 `busy_timeout=0`，若把检查放在 PRAGMA 之前，启动时残留 `-wal` 恢复的短暂锁竞争、另一实例运行/备份、Windows 上杀毒软件占用等都会误触发破坏性恢复）：

```sql
PRAGMA busy_timeout = 5000;               -- 先于检查设置（默认 0）
PRAGMA {integrity_check | quick_check};   -- full 逐行校验，quick 只查结构；单行结果
-- 检查通过后才执行 journal_mode/synchronous/foreign_keys（persist.rs:180-187）与 ensure_schema
```

- **结果分类（实现者必须按错误码分类，不得把一切 `Err` 当损坏）**：
  1. PRAGMA 执行成功、首行 `== "ok"` → 通过（多行结果 = 多条错误，同样进入恢复序列）；
  2. PRAGMA 返回 `Err` 且错误码为 `DatabaseBusy`/`DatabaseLocked`（含 `-wal` 恢复竞争、另一实例在运行/执行 `VACUUM INTO` 备份）→ 退避重试 3 次（200ms/500ms/1s）；仍失败 → `warn!`"integrity check skipped (busy)" 并**正常继续启动**，绝不进入恢复序列；
  3. PRAGMA 返回 `Err` 且错误码为 `NotADatabase`（文件内容损坏的典型信号）→ 进入恢复序列；
  4. 其他 `Err`（磁盘 I/O 错误、文件被第三方软件占用等）→ `error!` 记录原始错误后**跳过检查、正常继续启动**，交给后续 `load_from_db` 的既有非破坏性兜底（失败仅 warn + 空配置，`main.rs:177`），绝不改名/覆盖/删除。
  即：**破坏性恢复只由「检查成功执行但结果 ≠ ok」与 `NotADatabase` 两类信号触发**。
- **默认 `full`**：`data.db` 是配置库（点位规模在千级、库体积 MB 级以下），全量检查耗时毫秒级，只在启动时执行一次；`quick` 与 `off` 供超大库或特殊场景降级。
- **恢复序列（仅上述第 1、3 类触发）**，每一步都定义失败分支（日志全部 `error!`/`warn!` 带路径与首条错误）：
  1. 把 `data.db`（连同 `-wal`/`-shm`）改名/移动为 `data.db.corrupt-<unix秒>` 留证，不直接删除。**改名/覆盖失败**（Windows 上目标被其他进程占用时 rename 会失败）→ `error!` 告警后**停止恢复、按「检查未通过但文件未动」继续启动**（后续加载失败走既有空配置兜底），由运维介入；不做删除、不做循环重试；
  2. 若 `data.db.bak` 存在：复制为 `data.db`，重新 `open`（再次走同一套分类检查），成功则 `warn!("recovered from backup")` 继续启动；复制失败同样落入"不动文件、告警继续"分支；
  3. 备份不存在或恢复后检查仍未通过：此时原文件已隔离为 `.corrupt-*` 留证，删除并按空库新建（与现有"加载失败以空配置继续"的兜底一致，`main.rs:177`），并 `error!` 明示配置丢失。
- **双实例约束**：恢复序列被 Busy/Locked 分类挡住了最常见的"另一实例在运行"误触发；Linux 上若确有双实例且旧实例持 inode 继续写被改名的文件，属部署错误，超出本次范围——需在部署文档注明**单实例运行 data 目录**的约束，且恢复动作的触发面已按上述分类收窄到最小。
- 该逻辑在 `Db::open` 内实现，`main.rs` 不感知细节；`quick_check`/`full` 的选择经 `Config`（新增 `db_integrity: String` + env `GATEWAY_DB_INTEGRITY`，默认 `full`）传入。

#### 关于"批量提交"的如实说明

单事务批量提交**已经存在**且本次不改其语义：快照保存是单事务 + `prepare_cached` + UPSERT/差集删除（`persist.rs:568-722`），上层 300ms 写合并（`state.rs:67-79`、`main.rs:244-257`），历史库已是"内存缓冲 + 批量事务"（`gateway/gateway-server/src/history.rs:281-317, 342-355`）。本项对"批量"的实际增量是：

1. users 存储并入共享连接后，其 10 处"每操作一连接一隐式事务"收敛为同一连接上的短事务，**消除现状的不对称**：users 侧（`busy_timeout=0`）遇快照写入会立即 SQLITE_BUSY 失败，快照侧则等锁 5s——共享单连接后两类访问在同一连接上串行，两种失败/等待模式同时消失（事务粒度不变，无需合并 users 操作——它们是用户触发的低频离散动作）；
2. 每次 save 不再重复付出 open + PRAGMA + ensure_schema 的固定成本，去抖窗口内的合并落盘因此更快，间接提高了"窗口内多次变更合为一次事务"的达成率；
3. 优雅退出 flush（`main.rs:359`）时追加一次 `PRAGMA optimize`（幂等、廉价，维护统计信息）。

### 3.4 功能项三：`data-plane-filters`（死区、变化上报、滑动窗口聚合）

#### 3.4.1 切入点（精确到行）

唯一插入点：`manager.rs` 的 `poll_group_once()` 成功分支 `Ok(Ok(values))` 内，位置在**规则求值之后、`last_values` 缓存与 `GroupData` 构造/发布之前**。改造后的执行序（标注现有行号）：

```text

  Ok(Ok(values)) =>                                       manager.rs:1159
    1. rules::evaluate_and_fire(store, ..., &values)      manager.rs:1160-1170   【不动】规则永远看原始值

                            synthetic: Vec<(TagId, DataValue)>,   // 窗口聚合虚拟点位（可能为空）
```

选这个点的理由（写死，实现者不得另选）：

- 在规则**之后**：规则条件判定需要每个采集周期的原始值，死区抑制若发生在求值前会造成边沿丢失（如温度贴着阈值抖动时 `for_ms` 计时被人为中断）。
- 在 `last_values` **之后**：管理台"实时值"的语义是"设备最近一次上报的真实值"，与是否被过滤无关（死区只压北向流量，不应让监控页显示旧值）。
- 在 `bus.publish` **之前**：北向订阅者、旁路历史库拿到的都是过滤后的数据流（历史库语义见 §4.4）；分区广播的 O(1) 投递成本与 Lagged 行为不受影响（`bus.rs:62-75`）。
- `read_tags`（按需读，`manager.rs:808-855`）与规则动作写值**不过滤**——它们是请求-响应路径，过滤只作用于周期性发布。

#### 3.4.2 运行语义

对组 G 的一个采集批次（`values: Vec<(TagId, DataValue)>`，批内时间 `ts_ms`）：

**A. 死区 + 变化上报（`mode = "on_change"` 时生效；`"passthrough"` 为默认，行为与现状完全一致）**

每个数值点位维护基线 `last_reported: Option<f64>` 与 `last_reported_ms: u64`：

- 首次采集（无基线）→ **上报**并写基线（策略新增/修改/重启后同理，保证消费方总能拿到起点值）；
- 绝对死区：`|v - last_reported| > deadband` → 上报；
- 相对死区（可选，与绝对死区满足其一即上报）：`|v - last_reported| > deadband_percent/100 × |last_reported|`（`last_reported == 0` 时退化为绝对比较）；
- 布尔/字符串/Bytes：仅值变化（严格相等比较）才上报，死区不适用；
- **心跳**：`max_report_ms > 0` 且 `ts_ms - last_reported_ms >= max_report_ms` → 无条件上报（保证消费方知道点位仍活着）；
- 未上报的点位**不更新** `last_reported`（若抑制期间前移基线，会吃掉后续合法的累计跳变）；仅当发生心跳上报时才同时刷新 `last_reported_ms` 与 `last_reported` 基线值。

**B. 滑动窗口聚合（`window` 配置存在时生效，独立于 A 的 mode）**

- 每个数值点位维护样本环形缓冲 `VecDeque<(ts_ms, f64)>`（布尔按 0/1 折算、字符串不进窗口，折算口径复用 `rules.rs:372-393` `numeric_values` 的转换规则）；每批追加后剪除 `ts < now - window_ms` 的旧样本；
- **发射时机挂在采集节拍上，不新增任务**：每批处理后检查 `now - last_emit_ms >= emit_ms` 且本窗口有新样本 → 发射；窗口语义 = "最近 `window_ms` 内的样本"（滑动），`emit_ms <= window_ms` 时窗口重叠，即标准滑动窗口。**必须向用户明示的边界**：发射只能在采集批次到达时发生，因此**有效输出周期 = max(emit_ms, 组 interval_ms)**——组 `interval_ms` 大于 `emit_ms` 时（如 60s 低频组配 `emit_ms=10s`），实际按采集节拍输出，`emit_ms` 只是下限而非承诺（配置表与校验均已注明，防止"配了 emit_ms 就按 emit_ms 出数"的误期望）；
- 每个参与聚合的点位产出 `aggregates` 指定的虚拟点位：命名 `{tag_name}_{agg}`（`agg ∈ avg|min|max|count|first|last`），值域 `f64`；`count` 为整数计数的浮点表示；
- 虚拟点位 TagId：窗口状态创建时用 `TagId(Uuid::new_v4())` 生成一次并缓存在运行态里（`gateway/gateway-sdk/src/types.rs:152-158` 确认 `TagId` 是 `pub Uuid` 新类型，可自由构造）；名称经 `synthetic_names` 并入 `GroupData.tag_names`——北向插件与历史库都按名取数（`gateway/gateway-sdk/src/messages.rs:21-23`、`gateway/gateway-server/src/history.rs:193-217`），TagId 本身不参与任何路由或持久化，因此**进程重启后虚拟 id 变化无影响**；
- 节点停止/设备断采导致无新样本时窗口自然停发（可接受并在文档注明）；设备恢复后从新样本重新累积。
- 窗口聚合**不经过死区过滤**（聚合输出本身就是降采样结果，再过滤无意义）；窗口输入永远是原始值（在 A 的过滤之前从 `&values` 取数）。

**C. 一批消息的组装**：`published`（经 A 过滤的真实点位）与 `synthetic`（本批到期的窗口输出）合并为一次 `bus.publish`——同组一条消息，北向无需处理两种消息形态；两者皆空才整批抑制。

#### 3.4.3 配置挂接方式（组级策略对象，完全复刻规则引擎先例）

**不放 Tag 上**（避免动 `gateway-sdk` 的 `Tag` 结构、FFI 序列化与 tags 表 schema），**不放全局环境变量**（死区天然按组/点位而异）。新增"组数据策略"，一 provid组最多一条：

```rust
// gateway/gateway-core/src/filters.rs
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
#[serde(rename_all = "snake_case")]
pub enum FilterMode { Passthrough, OnChange }

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct TagDeadband {
    pub tag_name: String,            // 组内点位名（校验存在性）
    pub deadband: Option<f64>,       // 绝对死区，>= 0 且有限
    pub deadband_percent: Option<f64>, // 相对死区 0.0..=100.0
}

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct WindowAgg {              // 聚合项
    pub kinds: Vec<String>,         // avg/min/max/count/first/last 的非空子集
}

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct WindowPolicy {
    pub window_ms: u64,             // 窗口长度，>= 100
    pub emit_ms: u64,               // 发射周期下限，>= 10（对齐 MIN_POLL_INTERVAL_MS）；有效输出周期 = max(emit_ms, 组 interval_ms)，发射挂在采集节拍上
    pub aggregates: WindowAgg,      // 所有数值点位统一输出这些聚合项
}

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct GroupPolicy {
    pub south_node_id: NodeId,      // 由路径注入，body 中冗余字段被忽略
    pub group_id: GroupId,
    #[serde(default)]
    pub mode: FilterMode,           // 默认 passthrough（serde default 需为 Passthrough）
    #[serde(default)]
    pub deadband: Option<f64>,      // 组级默认死区：on_change 模式下未单独配置的数值点位用它
    #[serde(default)]
    pub deadband_percent: Option<f64>,
    #[serde(default)]
    pub max_report_ms: u64,         // 心跳；0 = 不强制
    #[serde(default)]
    pub window: Option<WindowPolicy>,
    #[serde(default)]
    pub tags: Vec<TagDeadband>,     // 点位级覆盖，同名后条覆盖前条（校验时去重拒绝）
}
```

## 四、测试策略

> 原则与现状一致（`docs/功能实现清单.md` 第九节：107 个测试 + CI 强制）。下表明确每类验证的层级——**真机/真实服务**指需要外部实体（Modbus 从站、MQTT broker、浏览器）的端到端验证；**纯逻辑单测**指 `cargo test` 可覆盖的部分。本设计刻意把可判定的核心全部收敛为纯逻辑，把真机面压到最小。

### 4.1 `session-expiry`

| 验证 | 层级 | 内容 |
|---|---|---|
| 过期判定谓词 | 纯逻辑单测 | `Session::is_expired(now)` 的边界：`expires_at=None` 永不过期；`now == expires_at` 视为过期；ttl=0 不产生过期 |
| 登录写入过期时间 | 纯逻辑单测（内存库 + 小 ttl） | `login` 后 DB `token_expiry` 与内存 `expires_at` 一致；响应体含 `expires_at` |
| 启动加载过滤 | 纯逻辑单测 | DB 中预置 `token_expiry` 为过去/未来/NULL 三种行，`open` 后仅未来者可用 |
| 过期后 401 | **准集成**（现有 `rbac_env` 模式，`api/mod.rs:550-568`）：ttl=1s，登录后 `tokio::time::sleep(1.1s)` 再打受保护端点，断言 401；随后重新登录恢复 200 | 可接受 1 秒级真实等待，不引入假时钟 |
| 改密/登出/顶号与过期共存 | 纯逻辑单测 | 既有失效路径在新 `Session` 类型下行为不变（回归） |
| 浏览器端自动登出 | **真机验证**（人工）：把 `GATEWAY_SESSION_TTL_SECS=30`，登录后等 30s，任意操作应弹回登录页 | 前端 401 处理已有（`web/src/api.js:48-60`），仅需人工确认 |
| 静态 token 不受影响 | 纯逻辑单测 | `GATEWAY_TOKEN` 配置下 ttl 到期后静态 token 仍 200 |

### 4.2 `sqlite-conn-reuse`

| 验证 | 层级 | 内容 |
|---|---|---|
| Db::open 幂等 + PRAGMA 生效 | 纯逻辑单测 | `open` 两次返回的连接上 `journal_mode=wal`、`busy_timeout=5000`（复用现有断言风格 `persist.rs:1066-1087`）；schema 只建一次不报错 |
| 快照读写回归 | 纯逻辑单测 | 既有 `snapshot_roundtrip_preserves_nodes`、`incremental_save_updates_and_removes_rows`、`secret_is_encrypted_at_rest_and_decrypted_on_load`、`throttled_backup_creates_consistent_snapshot` 等原样通过（自由函数包装层保证，测试代码位于 `persist.rs:893-1159`） |
| integrity_check 门禁与分类 | 纯逻辑单测 | ① 正常库 `Db::open` 成功；② 人为写坏文件头（截断/随机字节覆盖前 4KB，产生 `NotADatabase` 或首行 ≠ ok）→ 原文件被移为 `.corrupt-*`；③ 有 `.bak` 时自动恢复且数据可读；④ 无 `.bak` 时空库启动；⑤ `IntegrityMode::Off` 对坏文件不做检查（open 成功，加载阶段按现有错误路径失败）；⑥ **Busy 分类**：先以另一连接持有写锁再 `Db::open` → 退避重试后 `warn` 跳过检查、正常启动、文件未动；⑦ **rename 失败分支**跨平台难以稳定模拟（Windows 句柄占用），列为人工验证项：占用 db 文件后触发恢复路径，断言文件未被动、进程继续启动 |
| 共享连接串行正确性 | 纯逻辑单测 | 多任务并发经 `db.with()` 混合读写快照与 users 表，最终数据一致（利用 tokio test 多任务 + spawn_blocking） |
| users 操作回归 | 纯逻辑单测 | `login/logout/create/set_password` 等既有断言在 `Db` 注入后全部通过（改构造签名，逻辑不动） |
| 启动路径真实验证 | **真机验证**（人工或脚本）：对一份真实 `data.db`（含若干节点/用户）启动网关，观察日志出现 integrity 通过信息；再用 SQLite CLI 手工破坏副本后启动，确认走恢复分支 | 生产启动序列（main.rs）只能在真实二进制上走通 |
| 性能对比（可选） | 现有 `gateway-bench` 持久化基准 | 复用连接前后 save 耗时对比，留档 `docs/bench/`（非门禁） |

### 4.3 `data-plane-filters`

| 验证 | 层级 | 内容 |
|---|---|---|
| 死区/变化上报状态机 | 纯逻辑单测（`filters.rs` 内，仿 `rules.rs` 测试风格，直接喂时间序列） | 首采必报；`|Δ| ≤ deadband` 抑制、`> deadband` 上报；相对死区含 `last=0` 退化；布尔/字符串仅在变化时上报；心跳到期强制上报且刷新基线；基线在抑制期间不前移 |
| 窗口聚合 | 纯逻辑单测 | 给定样本与时间序列：窗口裁剪（老样本出局）、`emit_ms` 到期才发射、发射后 `last_emit_ms` 前移；avg/min/max/count/first/last 数值精确；布尔 0/1、字符串不进窗口；`emit_ms > window_ms` 与重叠窗口两种形态 |
| 无策略零开销 | 纯逻辑单测 | `policy_for_group` 无策略时 `filters::apply` 立即原样返回（`published == 输入`、无状态写入） |
| 链路集成（manager 层） | 纯逻辑单测（不依赖真机） | **前提（已核实，实现者必须照做）**：gateway-core 目前没有任何 SouthPlugin 测试替身，其 `Cargo.toml` 也没有 `[dev-dependencies]` 段；plugin-sim 的输出是 wall-clock 正弦（`gateway/gateway-plugins/plugin-sim/src/lib.rs:106-124`：`20.0 + 5.0·sin(t·0.1)`，最大斜率约 0.5/s），确定性成立但只有平滑慢漂移、**构造不出跳变**。因此：在 gateway-core 的测试模块内新建 `FakeSouthPlugin`（`SouthPlugin` 仅 `meta/open/close/poll_group/list_groups/list_tags` 六个方法无默认实现，其余有默认，见 `gateway/gateway-sdk/src/plugin.rs:68-148`，替身体量很小；`poll_group` 返回测试预置的阶跃/慢漂移时间序列），经 `mgr.register_south("fake", …)` 注册，**不引入对 plugin-sim 的 dev-dependency**。用真实 `Manager`：挂 `on_change + deadband` 策略后订阅 bus（`manager.bus().subscribe_all()`），断言抑制期无消息、跳变时有消息且 `last_values` 仍持续更新（原始值）；挂窗口策略后收到含 `*_avg` 等 `tag_names` 条目的消息；整批抑制时 `south_published` 不增、`filters_suppressed` 增。plugin-sim 仅用于人工/端到端验证且只能覆盖慢漂移抑制路径 |
| 策略 CRUD 与校验 | 纯逻辑单测（`api/mod.rs` 测试风格，disable_auth + oneshot） | PUT 合法/非法（死区负数、未知 tag_name、emit_ms<10、空 kinds）→ 200/400；DELETE 后热路径回到透传；写权限 Operator+（`required_role` 断言） |
| 持久化回归 | 纯逻辑单测 | 保存带策略的快照 → 重载 → 策略一致；旧版快照（无 policies 字段 JSON）可加载 |
| 状态清理 | 纯逻辑单测 | `node_remove`/`group_remove` 后 `FilterState` 无残留条目；策略重 PUT 后基线重建（首采必报） |
| 真实北向端到端 | **真机验证**（人工/脚本）：plugin-sim 南向 + plugin-mqtt 北向 + 本地 broker（如 mosquitto）：`on_change` 下静默期 broker 无报文、跳变时收到、心跳按 `max_report_ms` 到达；窗口模式下收到 `温度_avg` 等字段 | 涉及真实 MQTT 服务与 FFI 插件，只能实测；cargo test 不覆盖此层 |

### 4.4 必须向实现者交代的测试边界

- `Manager` 层集成测试可用 plugin-sim 的确定性输出做到**无真机**验证主链路；但 MQTT broker、浏览器会话、破坏性磁盘场景（§4.2 启动路径）必须人工/脚本实测，自动化不覆盖。
- 窗口发射依赖采集节拍（§3.4.2-B），单测需注入时间序列而非真实 sleep；带真实等待的用例只允许出现在 session-expiry 的 1.1s 用例。

## 五、风险与回退

| # | 风险 | 影响 | 缓解 | 回退 |
|---|---|---|---|---|
| 1 | 共享 `Mutex<Connection>` 上长事务阻塞其他操作 | flush 期间 users 请求短暂等待 | 快照保存已被去抖限制为 ≥300ms 一次、库体量小；`with()` 内禁止嵌套与用户输入驱动的长循环 | `Db::open` 失败或运行期锁异常时可退回自由函数 `save/load`（按次开连接的旧路径，保留为兼容包装），配置回退无需改库结构 |
| 2 | integrity_check 误判 / 大库启动变慢 | 启动时间增加或对健康库误触发破坏性恢复 | 检查前先设 `busy_timeout`；`Err` 按错误码分类：Busy/Locked 退避重试后跳过继续、I/O 类错误不动文件继续启动，**仅「检查成功执行但结果 ≠ ok」与 `NotADatabase` 触发恢复**；恢复先把坏库移为 `.corrupt-*` 留证、改名失败有不动的兜底分支，绝不删原始证据；`GATEWAY_DB_INTEGRITY=quick/off` 可关 | 设 `off` 即完全跳过，行为回到现状（加载失败 → 空配置启动） |
| 3 | 升级后存量会话被强制重登录 | 运维侧一次性不适 | 在变更说明中明示（§3.2 行为 3 是安全优先的刻意选择）；无 TTL 配置（ttl=0）时完全兼容 | `GATEWAY_SESSION_TTL_SECS=0` 恢复旧行为 |
| 4 | 过滤误配置导致"北向看起来没数据" | 用户困惑 | 整批抑制有 `filters_suppressed` 指标与 `/api/data-flow` 展示；策略校验在写入时拦截明显错误；心跳 `max_report_ms` 保证流不彻底断 | DELETE 策略或 `mode=passthrough` 即恢复透传，立即生效（PUT 后下一个采集周期生效，无需重启节点——`poll_group_once` 每拍重新查策略） |
| 5 | 窗口聚合内存增长 | 内存占用 | 样本缓冲仅存 `window_ms` 内样本且点位数量 = 组内数值点位数；节点/组删除即 `forget`；`emit_ms >= 10ms` 下界防高频分配 | DELETE 策略释放全部窗口状态 |
| 6 | 快照 `policies` 字段与旧版本程序互通 | 旧程序读新库丢策略（不报错）；新快照导入旧版本同上 | `SNAPSHOT_VERSION` 维持 1，`#[serde(default)]` 双向兼容；变更说明注明"降级会丢策略配置，其他配置不受影响" | 降级前通过 `/api/export` 人工留档 |
| 7 | 历史库语义变化（记录上报口径） | 死区抑制期历史无新行 | §3.4.1/§3.4.4 已明确为设计语义；管理台实时值不受影响 | 策略 passthrough 即恢复全量记录 |
| 8 | `from_file` 漏配新配置字段 | 配置文件里的 TTL/integrity 设置不生效 | `config.rs:207-241` 的 `from_file` 是逐字段硬拷贝，实施清单（§6）把两个新字段列为同一步骤 | — |

**整体回退**：三项彼此独立、无共享数据结构改动（唯一的交叉点是 `UserStore` 构造签名变化与 `AppState` 增加 `db` 字段），可按功能项独立 revert；数据库 schema 变更只有"users 加列（可空）"与"新增 policies 表"两项，均为向前兼容的增量，回退代码后旧 schema 继续工作。

## 六、分步实施顺序

按依赖与风险排序，每步可独立编译、测试、提交。括号内为功能项 id 与关键落点。

1. **【session-expiry ①】配置与会话模型**：`Config.session_ttl_secs` + env + 默认配置文件（`config.rs`）；`users/store.rs`：`Session` 结构、`token_expiry` 列迁移、login 签发、open 传 ttl。跑通 §4.1 前三个纯逻辑单测。
2. **【session-expiry ②】校验与清理**：`role_of` 过期判定、启动加载过滤、改密/登出置空 `token_expiry`、登录响应 `expires_at`。补 §4.1 其余单测与 1.1s 准集成用例；更新直接构造 `UserStore::open` 的既有测试调用点。
3. **【sqlite-conn-reuse ①】`Db` 抽象与兼容包装**：`persist.rs` 新增 `Db`/`IntegrityMode`，`load_secret`/`save_secret` 迁为 Db 方法，自由函数保留包装；`AppState` 增 `db` 字段、`flush()` 改造、`main.rs` 装配。跑通 §4.2 前两类单测 + 全量既有持久化回归（**此步不含 integrity_check，先保证连接复用零回归**）。
4. **【sqlite-conn-reuse ②】integrity_check 与恢复**：`Db::open` 门禁 + 恢复序列 + `GATEWAY_DB_INTEGRITY` 配置。补 §4.2 integrity 单测。
5. **【sqlite-conn-reuse ③】users 并入共享连接**：`UserStore` 持 `Arc<Db>`，10 处调用点改写，删除逐操作开连接。补并发正确性单测；人工走一次真实启动验证。
6. **【data-plane-filters ①】策略模型与持久化**：`filters.rs` 的配置结构 + `Store` 存储 + `policies` 表/快照字段 + 校验函数。跑通持久化回归单测。
7. **【data-plane-filters ②】热路径与运行态**：`filters::apply` 死区/变化上报/心跳状态机（先不含窗口）+ `poll_group_once` 按精确行号插图 + 指标三件套 + `forget_node/forget_group` 清理挂点。跑通 §4.3 状态机与链路集成单测。
8. **【data-plane-filters ③】滑动窗口聚合**：窗口缓冲、节拍发射、虚拟点位与 `synthetic_names` 合并。跑通窗口单测。
9. **【data-plane-filters ④】API 与指标暴露**：policy 路由/鉴权/handler + `DataFlowMetrics` 三计数器接入 `/api/data-flow` 与 `/api/metrics` 文本。补 CRUD 单测。
10. **【data-plane-filters ⑤】前端**（最小改动）：组详情页加"数据策略"卡片（mode/死区/心跳/窗口表单），依赖既有 `api.js`。此项如工期紧张可后置——后端 API 已自足，前端未上时可用 HTTP 直接配置。
11. **真机验证收尾**：§4.1 浏览器登出、§4.2 真实启动/破坏恢复、§4.3 sim+mqtt 端到端；三项各留一条验证记录。

> 每步完成后运行 `cargo test` 与 `cargo clippy -D warnings`（CI 已强制，见 `docs/功能实现清单.md` 第九节）；本设计不要求运行全量构建以外的新增 CI 配置。
