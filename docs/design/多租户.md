# 多租户数据域隔离（形态 B）——详细设计

> 功能项 id：`multi-tenancy`（`docs/功能实现清单.md` §七「多租户」，状态 ❌ → 本设计后转 🚧/✅）
> 上游决策：`docs/多租户决策方案.md` 已选定**形态 B（单实例 + 数据域隔离 / "软多租户"）**，本文件把其 B1–B6 步骤落成可实施的详细设计。
> 本文自包含：实现者只需读本文与文中引用的源码文件，无需回看决策与评审过程。
> 说明：文中「域」= 租户（tenant），两个词混用；代码标识统一用 `tenant`。

---

## 1. 目标与范围

### 1.1 目标

在同一网关实例内引入「域（tenant）」维度，使**不同域的用户默认只能看到和操作本域的数据**：

- 节点、组、点位、规则、北向订阅、历史数据按域可见、可操作；
- 用户登录会话携带域；Admin 角色跨域可见（**可见性隔离**，回答决策文档 Q2——不是存储层强隔离，过滤在 API/服务层完成）；
- 规则动作、北向订阅**默认拒绝跨域**（避免 A 域规则写 B 域设备）；
- 存量单租户数据平滑迁移到内置 `default` 域，老库升级零手工干预；
- 提供 `GATEWAY_ENFORCE_TENANTS` 灰度开关，可一键回到形态 A 行为。

### 1.2 对决策文档三个待拍板问题的回答（本设计采用）

| 问题 | 决定 |
|---|---|
| Q2 可见性隔离 vs 强隔离 | **可见性隔离 + 默认拒绝**：过滤集中在 API 服务层（`gateway-server`），core 存储不按域物理分库；Admin 跨域可见可操作；域不匹配的资源一律返回 404（不泄露存在性） |
| Q3 设备是否多域共享 | **v1 不支持**：一个节点只属于一个域。跨域引用需求一律通过「在目标域重建节点」解决；设备引用表与冲突策略不做（列入非目标） |
| Q4 按域配额 | **不做**：License 点位上限（`tags_total_count`，`handlers.rs:1351`）保持实例全局口径；配额模型属形态 C |

### 1.3 最小可用切片（MVP）——必须一次交付的内容

**MVP = 下列全部，缺一则租户功能不成立：**

1. 租户注册表 + 内置 `default` 域（`tenants` 表 + `/api/tenants` CRUD，Admin）；
2. 用户归属域：`users.tenant_id` 列、登录会话携带域、用户管理接口可指定域；
3. 数据归属：`NodeConfig.tenant_id`、`Rule.tenant_id`（组/标签/订阅经节点继承），持久化 schema v2 + 存量自动迁移；
4. 鉴权过滤：`AuthContext.tenant` + 集中式域校验入口（`api/scope.rs`）+ 全部节点级/列表/创建端点改造；
5. 历史隔离：`history.db` 的 `samples.tenant_id` 列 + 写入盖章 + 查询过滤 + 迁移；
6. 跨域动作防护：北向订阅同域校验（**API 与快照两条写入路径共用过滤器**，§3.5.3）、规则 source/动作同域校验；
7. `GATEWAY_ENFORCE_TENANTS` 灰度开关；
8. 前端：用户页域字段 + 域管理区块 + i18n。

### 1.4 非目标（明确不做）

- 形态 C（SaaS：控制面、计费、自助开通注销、配额）；
- 审计表（决策文档 B6）→ **第二切片**，见 §6 步骤 T7；
- 按域的历史删除/导出 API（schema 加列后只是两条 SQL 的事，v1 不暴露接口）；
- 域级配额、域级 License；
- 插件/FFI 层的租户语义（租户是**宿主侧**概念，`GroupData`、`gateway-sdk` 类型、FFI ABI 一律不改）。

## 3. 方案

### 3.1 依赖选型：零新增依赖

本设计**不引入任何新 crate**。所需的全部能力均由工作区既有依赖提供（以下每一个都在 `gateway/gateway-server/Cargo.toml` 与 `gateway/gateway-core/Cargo.toml` 中实际核实过，非凭记忆）：

| 能力 | 既有依赖（版本） | 用途 |
|---|---|---|
| SQLite 列迁移、租户表、历史过滤 | `rusqlite = "0.31"`（bundled，两端 Cargo.toml 均有） | `PRAGMA table_info` + `ALTER TABLE ADD COLUMN`；tenants 表 |
| 租户 ID/类型序列化 | `serde = "1"` + `serde_json = "1"`、`uuid = "1"` | `TenantId` 字符串类型即可，不需要新 ID 库 |
| HTTP 层注入与校验 | `axum = "0.7"`（request extensions 已用于 AuthContext，`api/mod.rs:196`） | 中间件注入 tenant |
| 并发容器 | `dashmap = "5"`（core 已用） | token 缓存、store 不变 |

**为什么不用 JWT/嵌域 token**：本仓库会话模型是「不透明 UUID token + 服务端查表」（`users/store.rs:333-338` 登录生成 UUID、`:399-404` `role_of` 内存查表）。把域编码进 token 需要引入签名/过期语义（决策文档指出绝对过期本就是待办 B2），且改用户域后旧 token 的域会失真。继续用查表方案，登录时从 users 行读域写进缓存即可，零新依赖、域变更即刻可控（见 D-9 会话失效决策）。

**为什么不在 core 加租户注册表**：`tenants` 表与 users 同库（`data.db`，S16），归 `UserStore` 管（它已封装该库的 spawn_blocking 访问模式）；core 只需要 `NodeConfig.tenant_id` 这个字符串字段，保持 core「不知道租户体系、只携带归属」的薄耦合。

### 3.2 租户模型与归属

#### 3.2.1 类型定义（新增于 `gateway-server/src/api/mod.rs` 或独立 `api/scope.rs`）

```rust
/// 租户 ID：非空短横线字符串（slug），如 "default"、"plant-a"；持久化为 TEXT。
/// 内置域 "default" 随迁移创建，不可删除。
pub type TenantId = String;
pub const DEFAULT_TENANT: &str = "default";

/// 会话的域作用域。All 只授予平台级身份，不落库。
#[derive(Clone, Debug, PartialEq, Eq)]
pub enum TenantScope {
    All,          // Admin / 静态 token / disable_auth / 未初始化
    One(TenantId), // Operator / Viewer 的用户域
}

#[derive(Clone, Debug)]
pub struct AuthContext {           // 扩展现有结构（api/mod.rs:33）
    pub role: crate::users::UserRole,
    pub username: Option<String>,
    pub tenant: TenantScope,
}
```

判定规则（中间件内实现，集中一处）：

| 身份来源（现状见 S2） | role | tenant |
|---|---|---|
| `disable_auth=true`（api/mod.rs:109） | Admin | All |
| 静态 `GATEWAY_TOKEN`（:150） | Admin | All |
| 无用户且无静态 token 的「未初始化」放行（:161） | Admin | All |
| 用户 token | 用户角色 | **Admin → All；Operator/Viewer → 其 users.tenant_id** |

> `enforce_tenants=false` 时中间件一律注入 `All`（行为完全回到形态 A），见 §3.3。

#### 3.2.2 归属规则（回答 ask 要求的「节点/组/标签/规则/历史」归属）

| 对象 | 归属方式 | 存储 | 理由 |
|---|---|---|---|
| 节点（南/北向） | **域的所有者** | `NodeConfig.tenant_id`（`gateway-core/src/node.rs:9`）+ `nodes.tenant_id` 列 | 节点是设备连接的唯一入口，域边界画在这里即可覆盖组/标签/读写 |
| 组、标签 | **继承所属节点**（访问时经节点求域） | 不加列 | 组/标签从不独立跨节点引用（`store.rs:78-227` 全部以 node_id 为前导键），冗余存储只会引入不一致 |
| 北向订阅 | 项级隐式继承：`(north, south, group)` 合法当且仅当 north 与 south 节点同域 | 不加列 | `manager.rs:313-350` 已按存在性过滤，追加同域过滤即可（§3.5.3） |
| 规则 | 规则行**冗余携带** `tenant_id` | `Rule.tenant_id` + `rules.tenant_id` 列 | 规则的 source 节点可能被删除（删除节点不清规则，`manager.rs:278-304` 无级联），查询过滤需要独立归属；创建/更新时以 source 节点域盖章并校验 |
| 历史样本 | 写入时从节点解析域，**冗余落列** | `samples.tenant_id` + 复合索引 | 节点删除后历史仍按保留策略留存（history.rs 只按 retention/max_rows 清理），查询期反查会失效；决策文档 B4 亦选择加列 |
| 用户 | 每用户一个域 | `users.tenant_id` 列 | 决策文档 B1 |
| 最近值缓存（`manager.rs:164-170`）、节点日志、离线队列 | 经节点继承 | 不改 | 键均含 NodeId 或按 NodeId 命名 |

#### 3.2.3 数据面（总线）为什么不需要改

南向 → 总线 → 北向的链路（`CLAUDE.md`「Data Flow」）：`GroupData` 只有 `node_id/group_id`；北向能收到哪些组完全由订阅表决定（`manager.rs:356-…` 按订阅键 `subscribe_groups`）。**只要订阅表的两条写入路径——API `set_north_subscriptions`（manager.rs:313-350）与快照 `apply_snapshot`（:605-610，服务启动加载与 restore）——都强制同域（§3.5.3），北向插件收到的数据天然全部本域**，总线广播层无需按域过滤，插件 FFI ABI（`gateway-sdk`、`docs/SDK与插件开发.md` §八）零改动。这是本设计最重要的集成判断：**域在配置面（store/API）封闭，数据面自动封闭**。注意其成立前提：订阅写入路径**没有第三条**（全局检索确认订阅表仅这两处写入），任何新增写入路径必须接入同一过滤器。

### 3.3 配置项

沿用 `enforce_roles` 的既有模式（`config.rs:42`、`:344-346`）：

| 配置 | 位置 | 默认 | 说明 |
|---|---|---|---|
| `GATEWAY_ENFORCE_TENANTS` | env（`config.rs from_env()`）<br>（不进 `config/gateway.json`，与 enforce_roles 一致——它也未进 ConfigFile） | `true` | `0`/`false` 时全局关闭域过滤：中间件注入 `All`，一切端点回到形态 A 行为。启动时打 `warn`（仿 `disable_auth` 告警，`main.rs:215-221`） |
| `tenants_enabled`（派生） | 无 | — | 是否创建 `/api/tenants` 路由不单独设开关：租户 API 永远存在但幂等（`default` 域不可删）；域过滤强度只由 `GATEWAY_ENFORCE_TENANTS` 控制 |

**盖章与过滤解耦**：开关只控制「过滤」，不控制「盖章」——无论开关与否，`create_node`/`create_rule`/历史写入都照常写 `tenant_id`。这样关闭期间新增的数据仍带正确归属，重新打开开关即时生效、无需二次迁移。

**优先级语义**：env var > 默认值（`true`），与 CLAUDE.md「Priority: env var > config/gateway.json > defaults」一致。

#### 3.4.5 域值的存储真相与读写口径（单一真相）

评审修订点：明确 nodes 的域「列」与「结构体字段」谁是真值，杜绝运维排障踩坑。事实基础：`nodes.config` 列**只存 `PluginConfig`**（`persist.rs:594` `serde_json::to_string(&n.config.config)`、load 侧 `:320-321` 按列重建 NodeConfig），即 **DB 中不存在「列 + config JSON」双写域值**。三层口径如下：

| 层 | 域值位置 | 谁以它为准 |
|---|---|---|
| 运行时 | `Store` 内 `NodeConfig.tenant_id` / `Rule.tenant_id` | `resolve_node`、所有域过滤、`GET /api/tenants` 的 `nodes_count`、迁移后的一切业务判断 |
| SQLite（data.db） | `nodes.tenant_id` / `rules.tenant_id` / `users.tenant_id` 专属列 | **DB 唯一持久化位置**；`save_to_db` UPSERT 写列、`load_from_db` SELECT 读列（§3.4.2-a），与内存互为镜像 |
| 快照 JSON（备份/restore/内存构建） | 随 `NodeConfig`/`Rule` serde 序列化（`Node` 经 `#[serde(flatten)]`，node.rs:22-24） | restore/启动加载以此值进入内存；DB 列值不参与快照 |

推论（写入实现约束与运维文档）：

1. 正常路径两处一致（同一次 save/load 转换）；**手工 `UPDATE nodes SET tenant_id='x'` 只改列，运行时不生效**，且会在下一次任意变更落盘时被内存值覆盖（增量 UPSERT 以内存快照为准，persist.rs:568-722）——改域唯一途径是**删除并重建节点**（§3.6.3），运维 SQL 仅限灾备核对；
2. 迁移补章（§3.4.2-a 第 3 步）发生在启动加载**之前**（load 先读列），内存与列天然一致；
3. `GET /api/tenants` 的 `nodes_count` 从内存 Store 统计，不读列。

#### 3.5.1 集中入口：`api/scope.rs`（新文件）

决策文档的核心风险是「漏一个查询条件就是跨租户数据泄露」。对策是把域校验收敛到**唯一的节点解析入口**，而不是期望每个 handler 记得加条件：

```rust
/// 所有 /nodes/:id/* 端点与「按 node_id 定位资源」的端点必须经由本函数取节点。
/// 域不匹配（One 域 ctx 访问他域节点，或节点不存在）一律 404 —— 不区分，防存在性探测。
pub fn resolve_node(
    state: &AppState,
    ctx: &AuthContext,
    raw: &str,
) -> Result<(NodeId, gateway_core::Node), ApiError> {
    let nid = parse_node_id(raw)?;                    // handlers.rs:17-21 原函数移入/复用
    let node = state.manager.node_get(nid)
        .ok_or_else(|| ApiError::not_found("node not found"))?;
    if !tenant_allows(&ctx.tenant, &node.config.tenant_id) {
        return Err(ApiError::not_found("node not found"));
    }
    Ok((nid, node))
}

fn tenant_allows(scope: &TenantScope, owner: &str) -> bool {
    matches!(scope, TenantScope::All) || matches!(scope, TenantScope::One(t) if t == owner)
}

/// 列表端点用
pub fn scoped_nodes(state: &AppState, ctx: &AuthContext) -> Vec<Node> { /* 按 tenant_allows 过滤 nodes_list() */ }
```

#### 3.5.3 数据面同域校验（core 侧：订阅的两条写入路径共用一个过滤器）

评审修订点：订阅表有**两条写入路径**——API `set_north_subscriptions`（manager.rs:313-350）与 `apply_snapshot` 的订阅直灌（:605-610，`t.clear()` 后逐项 `t.insert`，现无存在性/同域过滤），后者被启动加载（`main.rs:173`）与 restore（`handlers.rs:632`）共用。只改 API 路径会让「伪造/异地导入的 v2 备份携带跨域订阅项」经 restore 注入内存订阅表，北向插件将持续收到他域数据——直接击穿 §3.2.3 的核心判断，且与 API 路径口径不一致（Admin 经 API 也被过滤，restore 却注入得进去）。因此把过滤抽成**唯一共享函数**，两条路径都必须经过：

```rust
// manager.rs 新增私有方法
/// 订阅项合法性过滤（南向存在 + 是南向 + 组存在 + 与北向节点同域）。
/// set_north_subscriptions 与 apply_snapshot 共用：订阅表不存在第三条写入路径（§3.2.3）。
fn filter_subscriptions(
    &self,
    north_node_id: NodeId,
    subs: Vec<GroupSubscription>,
) -> Vec<GroupSubscription> {
    // 北向节点自身必须存在（坏快照引用不存在节点：丢弃该节点全部订阅项）
    let Some(north) = self.store.node_get(north_node_id) else { return Vec::new() };
    subs.into_iter().filter(|s| {
        let Some(n) = self.store.node_get(s.south_node_id) else { return false };   // 既有过滤（:318-328）
        if n.kind() != NodeKind::South { return false; }
        if self.store.group_get(s.south_node_id, s.group_id).is_none() { return false; }
        match (north.config.tenant_id.as_str(), n.config.tenant_id.as_str()) {
            (a, b) => a == b,   // 两端域均由迁移保证非空（§3.4.2），恒可比
        }
    }).collect()
}
```

接入点：
1. `set_north_subscriptions`（:313-350）：现有内联过滤器（:318-328）整体替换为 `let subs = self.filter_subscriptions(north_node_id, subs);`，其余逻辑（重启消费任务、通知插件）不变；
2. `apply_snapshot`（:602-610）：订阅插入改为 `t.insert(*nid, self.filter_subscriptions(*nid, subs.clone()));`——注意该调用发生在 `apply_to_store`（:604）之后，Store 已灌入节点，域可查；过滤是**内存表层面的收敛**，不回写快照源（restore 的外来快照与 data.db 均不重写），下一次任意变更落盘时内存表自然持久化，DB 内残留的跨域行不再被加载进内存、无害。顺带修复既有缺陷：旧路径不滤「引用已删除南向节点的订阅项」，共享函数一并覆盖。

restore 侧（handlers.rs:569-638）因此天然防住跨域订阅注入；§4.2-8 的恢复测试必须断言这一点（API 路由矩阵抓不到该绕过）。

规则引擎热路径 `rules_by_group`（store.rs:250-258）**不改**：它按 `(south_node, group)` 匹配，规则域已在创建时与 source 节点对齐（§3.5.2），采集回调无需知道域，零性能开销。

### 3.6 与现有机制的集成

#### 3.6.1 持久化与存量迁移（一次启动完成，零手工）

触发点分两处（各归各的 schema 所有者，见 §3.4.2）：
`persist::ensure_schema`（persist.rs:163-173，load 与 save 前都会执行）负责 nodes/rules/meta；`UserStore::open`（users/store.rs:182-247）负责 users/tenants。

流程：
1. persist 侧：`PRAGMA table_info(nodes)`：无 `tenant_id` 列 → `ALTER TABLE nodes/rules ADD COLUMN`（§3.4.2-a）；`UPDATE meta SET version = 2`；按 source 节点为存量规则补章——孤儿规则（source 节点已删）保持 `default`（可见于 default 域的 Admin，行为与迁移前一致）；
2. users 侧：`PRAGMA table_info(users)`：无列则 ALTER；`tenants` 表 `CREATE TABLE IF NOT EXISTS` + `INSERT OR IGNORE 'default'`（§3.4.2-b）。执行顺序晚于 persist 侧（main.rs:198 vs :154），不依赖其结果。**失败语义必须 fail-closed（评审修订点）**：`UserStore::open` 任一迁移步骤失败返回 `Err` 时，main.rs 不得走现状的 `UserStore::empty()` 降级（main.rs:198-204）——`empty()` 的 `has_any_user()` 恒为 `Ok(false)`（users/store.rs:628-632），而认证中间件在「无静态 token 且无用户」时按未初始化放行 Admin（api/mod.rs:160-171），实例会静默退化为无凭据管理员模式。改为 error 日志 + 启动失败退出；`UserStore::empty()` 构造函数保留供测试构造「禁用态」（api 测试不受影响），仅生产入口不再用它兜底（有意收紧 store.rs:131 注释所述「打开失败保证服务仍能启动」语义）；
3. 全新安装（无 data.db）：v2 的 CREATE TABLE 自带新列，ALTER 路径不触发，两条路径行为一致。

时序与并发：迁移发生在启动路径（`main.rs:154` `persist_load_secret` 之前由 `ensure_schema` 完成）且 WAL 下 `busy_timeout=5000`（persist.rs:180-187），单进程部署无竞争。`data.db.bak` 节流备份（persist.rs:794-823）继续提供回滚点；升级前建议运维手动 `POST /api/backup`（文档化）。

`history.db` 迁移在 `HistoryRecorder::start` 建库处（history.rs:126-129 `execute_batch(SCHEMA)`）加同样的「判列 → ALTER → 重建索引」块。存量样本归 `default` 域——与 nodes 全部迁入 `default` 一致，即**升级后任何既有用户看到的范围与升级前完全相同**（现网只有 default 一个域）。

旧版 `data.json` 路径（main.rs:147-153 → `load_json`）：`NodeConfig.tenant_id`/`Rule.tenant_id` 的 `#[serde(default)]` 使 v1 JSON 原样读入并落 default 域，无需改迁移代码。

#### 3.6.2 备份 / 恢复

- 备份文件内容是 `Snapshot` JSON（backup.rs:66-68），v2 快照自动带域，备份格式魔数 `GWBK|2`（backup.rs:19-20）**不变**；
- `restore`（handlers.rs:569-638）版本门禁 `snap.version != SNAPSHOT_VERSION`（:602）放宽为 `snap.version > 2 → 400`；`snap.version == 1` 时**内存补章**：全部 node/rule `tenant_id = "default"`，打 info 日志——旧备份在升级后仍可恢复，不强制重新导出；
- **restore 不放行跨域订阅**：恢复最终走 `manager.apply_snapshot`（handlers.rs:632），订阅插入经 §3.5.3 共享过滤器——伪造/异地备份即使携带「域 A 北向 → 域 B 南向组」项也会在内存表中被滤除（不回写快照文件）；
- License 前置校验（:611-631）不动（点位上限仍全局）。

#### 3.6.3 插件 / FFI / 进程隔离

零改动：`gateway-sdk` 类型（`gateway-sdk/src/types.rs` 全文核实：Tag/Group/DataValue 均无归属概念）、`export_*_plugin!` ABI、`gateway-plugin-host` 进程隔离（CLAUDE.md「Plugin System」）不感知域。域变更（节点换域）通过「删除重建节点」实现——节点 id 会变，北向订阅需重配；不做「改域」API（改域会破坏历史归属连续性）。

#### 3.6.4 会话与用户

- 登录：`UserStore.login`（store.rs:260-374）读出 `UserRow.tenant_id` 随 `(token, user)` 返回；token 缓存写入 `(role, tenant_id)`；
- 改域/改角色：`update_simple` 涉及域变更时清 token（§3.4.3），避免旧会话残留旧域；
- 静态 token 与未初始化身份恒为 All（§3.2.1）。

#### 3.6.5 前端

见 §3.4.4。登录页（`Login.vue`）不改；登录响应中的 `user.tenant` 可在顶栏展示（可选，非 MVP 必需）。

## 4. 测试策略

分级标注：【A】纯逻辑单测（无 IO）；【B】真实服务/真实文件验证（本地可跑：真实 SQLite 临时文件、axum oneshot Router）；【C】真实外部服务或真机（本地 MQTT broker / 现场设备，手动或可选 CI job）。

### 4.1 【A】纯逻辑单测

1. `TenantScope` 判定：`tenant_allows` 全组合（All×任意=真；One(default)×default=真；One(a)×b=假）；空/未知域拒绝。
2. serde 向后兼容：v1 形状 JSON（无 `tenant_id`）反序列化 `Node`/`Rule` 得 `default`；v2 序列化 roundtrip。
3. `required_role` 不受租户影响：既有断言（api/mod.rs:589-644）原样保持通过。
4. `validate_interval_ms` 等既有纯函数回归不受影响（冒烟即可）。

### 4.2 【B】真实 SQLite / axum 验证（核心，能且必须在 CI 跑）

5. **data.db 迁移**：手工构造 v1 库（按 persist.rs:23-70 旧 SCHEMA 建表插行、meta.version=1）→ 调 `ensure_schema` → 断言：nodes/rules 新增列存在且为 `default`、meta.version=2、原行数不变、孤儿规则保持 default；users 侧同法单独构造（无列 users 表 → `UserStore::open` 迁移 + tenants 表出现且含 default）。幂等：二次 open 不再变更。
6. **history.db 迁移**：同法构造旧 samples 表 + 插入行 → 迁移 → 断言列、索引 `idx_samples_series_t` 存在、旧行可按 default 域查出。
7. **快照 roundtrip（v2）**：两个域的节点/规则保存后加载，域不串。
8. **恢复与快照加载的订阅同域过滤（评审修订点）**：用 v1 形状 Snapshot 走 `encrypt_backup` → `decrypt_backup` + 补章逻辑 → 断言全部落 default；v2 备份直接恢复域保持。**另构造含跨域订阅项的 v2 快照**（域 A 北向节点 → 域 B 南向组、以及引用已删除南向节点的孤儿项）→ 直接调 `Manager::apply_snapshot`（不经任何 API，模拟伪造备份/异地导入）→ 断言 `get_north_subscriptions` 中跨域项与孤儿项均被滤除；同断言覆盖启动加载路径（同一函数）。注意：此绕过发生在 core 层，**§4.2-9 的 API 路由矩阵抓不到它**，本用例是唯一防线验证。
9. **API 跨域矩阵**（复用 `rbac_env` 夹具，axum oneshot）：
   - 域 A operator token 访问域 B 节点的全部节点级路由（§3.5.2 第一类逐一枚举）→ **404**；
   - 域 A viewer `GET /nodes` 只见 A；`GET /rules` 只见 A；
   - 域 A operator `POST /nodes` 自动落 A；传 `tenant=B` → 404；
   - 域 A admin（角色 Admin）`GET /nodes` 见全部；
   - `POST /nodes/:id/write_tags` 跨域 → 404（在 RBAC 403 之前已被存在性挡住，断言顺序）；
   - `PUT /nodes/:id/subscriptions` 携带跨域项 → 该项被过滤（响应/后续 GET 验证）；
   - `POST /rules` source 指向域 B 节点 → 400；
   - `GET /history/series` 域 A token 查域 B 节点序列 → 空结果；
   - `GET /tenants` operator → 403；admin → 200；
   - `DELETE /api/tenants/default` → 400。
10. **enforce_tenants=0 回退**：同矩阵但 `Config.enforce_tenants=false` → 跨域访问 200（形态 A 行为）；数据盖章仍正确（DB 断言）。
11. **token 缓存**：改用户域后旧 token 的 `auth_of` 返回新域（强制重登录生效）；logout 失效不变。
12. **规则热路径回归**：`rules_by_group` 对两域同组名规则不串（纯内存，归 A/B 边界均可，按 core 既有测试风格放 core）。
13. **users 侧迁移失败 fail-closed（评审修订点）**：把 users 迁移批次抽成 `ensure_users_schema(conn) -> Result`，用只读连接（`OpenFlags::SQLITE_OPEN_READ_ONLY`）打开含 v1 users 表的临时库调用之 → 断言返回 `Err` 且 `UserStore::open` 将其传播为启动错误；并断言 main 入口逻辑（或等价的构建函数）在 open 失败时**不**回退 `UserStore::empty()`（否则「未初始化」放行分支会造成无凭据 Admin，见 §3.6.1）。

### 4.3 【C】真实外部服务 / 真机（手动验证清单，不进默认 CI）

14. 本地 MQTT broker（如 mosquitto）：域 A 北向节点订阅域 A 南向组正常上报；北向**无法**订阅域 B 组（订阅项在 `set_north_subscriptions` 与 `apply_snapshot` 均被滤除，broker 层观察 topic 无 B 域数据）——本质是 4.2-8/4.2-9 的端到端复验；离线队列文件仍按节点隔离。
15. Modbus 真机/模拟器：域 B token 写域 A 设备 → 404，设备无写流量（抓包或设备侧寄存器观察）。
16. OPC UA / virb 节点跨域读写同上（抽样一种即可）。

### 4.4 明确不验证

- Prometheus 端点按域抓取（设计保留全局，§3.5.4）；
- 主日志行级脱敏（§3.5.4）。

|---|---|---|---|---|
| R1 | 漏掉某个写入/查询路径的域条件 → 跨域泄露（决策文档点名的首要风险；评审证实订阅快照路径即一例） | 高 | 集中入口 `resolve_node`（默认拒绝）；**订阅表两条写入路径共用 `filter_subscriptions`**（§3.5.3）；路由矩阵测试逐路由断言 + `apply_snapshot` 直灌测试（4.2-8，API 矩阵抓不到 core 层绕过）；`scope.rs` 模块级注释 + PR 检查单禁止绕过；跨域一律 404 防探测 | `GATEWAY_ENFORCE_TENANTS=0` 立即回到形态 A 行为（无需回滚代码） |
| R2 | schema 迁移丢/坏数据 | 中低 | `ALTER TABLE ADD COLUMN DEFAULT` 非破坏；迁移幂等（判列再改）；`data.db.bak` 节流备份 + 升级 SOP 要求先 `POST /api/backup`。**persist 侧**失败 → `persist_load` 报错走既有「warn + 空配置」路径（main.rs:177），不 crash 但需人工介入。**users 侧**失败不允许对称降级：现状 `UserStore::empty()` 兜底（main.rs:198-204）叠加「未初始化放行」分支（api/mod.rs:160-171，empty 的 `has_any_user()` 恒 `Ok(false)`，users/store.rs:628-632）会静默退化为**无凭据 Admin**（fail-open）——本设计改为 fail-closed：迁移失败传播为启动错误，拒绝服务（§3.6.1、测试 4.2-13） | persist 侧：用 `.bak` 恢复或还原备份文件后回滚二进制；users 侧：按 error 日志修复库（如磁盘/权限问题）后重启——宁可不启动，不可无凭据放行 |

| R5 | 两域引用同一台物理设备（重复建节点）→ 写反控互相影响 | 中 | v1 明确禁止跨域共享（§1.2 Q3），域内重复引用与现状同等（单租户本就无防呆）；部署文档写明 | 不适用（约束为运维规范） |
| R6 | 会话域滞后（改域后旧 token 仍旧域） | 低 | 改域即清 token 强制重登录（§3.4.3）；单会话模型（login 顶掉旧 token，store.rs:339-353）本就限制窗口 | — |
| R7 | 北向出口无域语义：两域共用同一 broker/topic_prefix 时数据在 broker 侧互见 | 中 | 网关侧同域订阅已保证进程内隔离；**broker 侧隔离是部署规范**：每域独立 `topic_prefix`（plugin-mqtt 每节点配置，plugin-mqtt/src/lib.rs:86-92）或独立 broker；写入部署文档 | 运维调整 |

## 附：实现者速查——关键决策清单

1. 域只落四处存储：`nodes.tenant_id`、`rules.tenant_id`、`users.tenant_id`、`samples.tenant_id`；组/标签/订阅/最近值/日志/离线队列一律经节点继承，不加列。
2. 节点级访问唯一入口 `resolve_node`，跨域/不存在统一 404；禁止 handler 内自行 `parse_node_id`+`node_get`。
3. Admin ⇒ TenantScope::All（跨域可见可操作）；Operator/Viewer ⇒ 其用户域；静态 token、disable_auth、未初始化 ⇒ All。
4. `GATEWAY_ENFORCE_TENANTS=0` 只关过滤不关盖章；默认开启。
5. `SNAPSHOT_VERSION=2`；迁移分两处幂等执行：persist 侧 `ALTER TABLE nodes/rules ADD COLUMN DEFAULT 'default'` + 规则按 source 补章 + meta 版本号（v2 建表语句自带新列），users 侧 `ALTER TABLE users` + 建 `tenants` 表（§3.4.2）；`history.db` 同法并重建复合索引。
6. restore 接受 version ≤ 2，v1 内存补 default 章；旧备份无需重新导出。
7. 订阅表仅两条写入路径——`set_north_subscriptions`（API）与 `apply_snapshot`（启动加载/restore）——必须共用同一个 `filter_subscriptions` 同域/存在性过滤器；数据面（总线/插件/FFI）零改动。
8. 规则域一律由服务端以 **source 节点域**盖章（请求传入值忽略）；规则写操作 Admin-only（api/mod.rs:75-78），不存在「One 域用户写规则」分支。
9. 零新增依赖（rusqlite/serde/uuid/axum/dashmap 均为既有版本）。
10. 域值单一真相：运行时以内存 `NodeConfig`/`Rule` 为准，`nodes.config` 列只存 `PluginConfig`（persist.rs:594），tenant 专属列是 DB 唯一持久化位置；手工 UPDATE 列不生效且会被内存值覆盖，改域只能删节点重建。
11. users 侧迁移失败必须 fail-closed（传播为启动错误），禁止回退 `UserStore::empty()`——否则与「未初始化放行」分支叠加成无凭据 Admin；persist 侧失败维持既有「warn + 空配置」语义。
12. metrics/health 保持全局口径、One 域禁拉 system/all 日志——两处残留泄露面如实文档化。
