## 2. v2.0 主题规划

> 量级口径：S ≤ 3 人日，M 3–8，L 8–15，XL > 15。均含测试与文档；门禁沿用
> fmt / clippy -D warnings / cargo test --workspace / 前端 build。

### T1 流程编排与告警引擎 v2 ⭐ 主线候选（XL，20–30 人日 MVP）

- **目标**：数据面可编排——源（南向采集/历史/手动）→ 处理（规则/过滤/聚合/脚本）→ 汇（北向/告警/存储）以 DAG 声明并可视化编辑；告警从「规则命中即发」升级为生命周期（产生/确认/恢复/升级）。
- **现状差距**：规则引擎 + filters 是单点流水线，无多级编排；无告警生命周期与告警中心页。
- **关键资产**：`redesign/v1-flow-orchestration` 分支（66 commits，+38.8k 行，2026-01~05）含 FlowEditor、flow 节点/边持久化、告警事件页的完整探索——**作为设计参考在当前 main 上增量重做**（该分支早于多租户/Review 加固，直接 graft 风险高，见 §6）。
- **范围切分（MVP→完整）**：① flow 数据模型 + 执行引擎（复用 bus/filters/rules 原语）→ ② 告警事件表 + 生命周期 API → ③ FlowEditor 前端重做（按需引入后 components.d.ts 体系内）→ ④ 告警中心页 + 通知渠道（复用北向插件）。

### T2 历史数据前端化（S–M，3–6 人日）—— ✅ 已完成（2026-11-08，M1 批次一）

- **目标**：补齐「后端已就绪、前端为零」的断层——历史曲线页（多点位叠加、时间范围、降采样展示）、历史报表导出。
- **现状差距**：`/history/series` 等三个 API 已实现（含租户过滤、分桶查询），前端无任何调用。
- **结果**：曲线页已落地（ECharts 按需、独立懒加载 chunk；序列多选 + 时间范围 + min/max 置信带；未启用态指引）；**执行过程中计划外发现并修复管理台 P0**（前端 BASE 与后端 v1 别名契约不匹配，登录等大部分请求自 `887d387` 起 404，详见 `docs/实施报告-v2.0.md` §1.2）；报表导出顺延至后续批次。

### T3 API v2（M，5–8 人日）

- **目标**：`/api/v2/` 版本化；列表类端点分页；写路径速率限制；OpenAPI-first codegen 扩展到全部端点。
- **现状差距**：路由级 OpenAPI 注解已有，但无版本化/分页/限流；契约类型仅部分生成。
- **约束**：v1 路径保留一个兼容期（时长见 §7 Q4），WS 协议同步升版。

### T4 运维与交付（M，5–8 人日）

- **目标**：容器镜像进 Release（当前 release.yml 只出 tar+SHA256SUMS）；`data.db` schema v2→v3 升级向导（就地迁移 + 回滚点）；nightly bench 自动与最近基线对比、越界告警。
- **现状差距**：镜像未发布；升级仅靠启动迁移；bench nightly 存档但不做对比判定。

### T5 质量纵深（M，持续）

- **目标**：长跑 soak 测试（72h+，覆盖 Lagged/重连/持久化退化）；规则/filters property tests；bench 按 README 口径自动化「3 次取中位数」对比。
- **现状差距**：测试 120+ 全绿但无 soak；bench 对比靠人工。

### T6 插件生态扩展（按需，每个 M）

- 候选：S7、SNMP、EtherNet/IP（南向）；OPC UA Server、SQL/WebSocket（北向）。**不在 MVP 范围**，按客户需求逐个立项（每个插件的实现路径已有成熟范式：SouthPlugin/NorthPlugin + FFI 双形态 + 真机联调）。

### T7 SaaS 化（多租户 C 形态）（XL，60+ 人日）——默认出范围

- 配额/计费/SLA/租户注销数据策略。仅当 §7 Q5 拍板「是」才启动；在此之前多租户维持形态 B。

## 3. 里程碑草案

| 里程碑 | 内容 | 出口条件 |
|---|---|---|
| **M1（v2.0-alpha）** | T2 历史曲线页 + T1-①②（flow 引擎 + 告警事件 API） | 全门禁绿；flow MVP 经 Docker 真机联调（沿用联调记录 §3.1 环境）；文档同步 |

合并策略：v2.0 分支承载全部开发；每个里程碑经 PR 回 main；main 期间只收 v1.x 缺陷修复。

## 4. 建议的第一步

1. **T2 历史曲线页**（3–6 人日）——后端零改动、纯前端 + 少量 API 增强（如需新增导出端点）；
   既是用户可见价值，也验证 v2.0 分支工作流。
2. **T1-① flow 数据模型设计稿**——先出 `docs/design/流程编排-v2.md`（数据模型/执行语义/与 rules-filters 的关系），
   把 redesign/v1 的经验教训（图配置保存映射、草稿保存、位置持久化等 66 commits 修过的坑）写进设计约束。

## 5. 风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| T1 范围蔓延（编排引擎是最容易过度设计的模块） | XL 变无底洞 | MVP 先限定「顺序 + 并行分支」两种拓扑，循环/子流程推后；调度器评估结论（共享轮不需要）沿用 |
| redesign/v1 参考代码与当前 main 语义漂移 | 误用过时模式 | 只取设计与交互经验，代码逐段重写；多租户/鉴权/license 门禁按 main 现行模式接入 |
| 历史页放大 SQLite 查询压力 | 影响采集主链路 | history 已是独立写线程 + 旁路订阅；查询加超时与分页，必要时先压测 |
| v2.0 开发期 main 仍在演进 | 合并冲突 | 里程碑粒度回 main；main 侧大改提前在 v2.0 公告 |

- **不直接合并**：早于多租户/24 项 Review 修复/缺陷批，文本零冲突 ≠ 语义零冲突（新 API 未经租户过滤、鉴权、license 门禁）。
