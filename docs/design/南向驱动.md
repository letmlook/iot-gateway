## 1. 目标与范围

### 1.1 目标

为网关新增四个南向驱动插件，作为独立 crate 加入现有 workspace，实现 `SouthPlugin` trait：

| 功能项 | crate 名 | 协议 | 典型设备 |
|---|---|---|---|
| `south-s7` | `plugin-s7` | Siemens S7（ISO-on-TCP，端口 102；S7Comm 与 S7CommPlus） | S7-300 / 400 / 1200 / 1500 |
| `south-bacnet` | `plugin-bacnet` | BACnet/IP（UDP 47808） | 楼宇自控：DDC 控制器、传感器、VAV |
| `south-ethernet-ip` | `plugin-ethernet-ip` | EtherNet/IP CIP 显式报文（TCP 44818） | Allen-Bradley CompactLogix / ControlLogix |
| `south-iec104` | `plugin-iec104` | IEC 60870-5-104（TCP 2404，主站/控制站角色） | 变电所 RTU、测控装置、保护装置 |

四个驱动均要求：轮询采集（`poll_group`）、点位校验（`validate_tag`）、按需读、写值（`write_tags`，
IEC104 走遥控命令）、配置/点位 Schema（中英文，前端自动生成表单）、`.dll/.so` 动态加载与
静态链接两种形态、进程隔离模式（`GATEWAY_PLUGIN_ISOLATION=process`）下可用——并且**两种
形态行为一致**（这一点直接约束了 IEC104 的架构，见 §3.6）。

### 1.2 范围外（明确不做）

- **BACnet MS/TP、BACnet/SC、BBMD/路由**：只做 BACnet/IP 单网段直连（上游 crate 亦仅支持此范围，见 §3.3）。
- **EtherNet/IP 隐式报文（Class 1 I/O）与 CIP 通用节点**：只做 Logix 符号标签的显式读/写。
- **IEC 104 被控站（服务端）角色**：本网关只做主站（controlling station）。
- **IEC 104 文件传输（F_FR_NA_1 等）、S7CommPlus 符号化寻址**：列入后续扩展，不进本期。
- **真机验证**：本环境无 S7/BACnet/AB/RTU 真机，真机验收不在本设计范围内（见 §4）。

## 2. 现状与衔接点

### 2.1 插件框架（全部复用，无需改动 gateway-sdk / gateway-core）

| 机制 | 位置 | 说明 |
|---|---|---|
| `SouthPlugin` trait | `gateway/gateway-sdk/src/plugin.rs:67-149` | `meta` / `config_schema` / `tag_schema` / `open` / `close` / `init` / `uninit` / `start` / `stop` / `setting` / `validate_tag` / `poll_group` / `write_tags` / `list_groups` / `list_tags` |
| `PluginConfig` | `gateway/gateway-sdk/src/types.rs:277` | `HashMap<String, serde_json::Value>`，取值方式见 `plugin-modbus-tcp/src/config.rs` 的 `config_str` / `config_u16` |
| `DataValue` | `gateway/gateway-sdk/src/types.rs:18-32` | `Bool / Int8..Int64 / UInt8..UInt64 / Float32 / Float64 / String / Bytes` |
| `Tag` / `TagAttr` | `gateway/gateway-sdk/src/types.rs:203-222` | `address: String` 是驱动的地址语法载体；`attr: Read / Write / ReadWrite` |
| `PluginError` | `gateway/gateway-sdk/src/error.rs:20-22,60-92` | 构造器 `msg / config_invalid / tag_invalid / connection_failed / timeout / not_supported` |
| FFI 导出 | 各插件 `src/ffi.rs`，一行 `gateway_sdk::export_south_plugin!(crate::XxxPlugin);` | 宏内置 panic 隔离；**每次 FFI 调用新建 current_thread runtime 并在调用结束时销毁**（`gateway/gateway-sdk/src/ffi.rs:337-342` `__gateway_plugin_block_on`）；契约见 `docs/SDK与插件开发.md` §8 |
| 宿主调用方式（动态加载） | `gateway/gateway-core/src/loader.rs:104-118` `run_sync` | 每次 FFI 调用在**独立作用域线程**上执行，插件内 `block_on` 安全；调用返回线程即结束 |
| 宿主调用方式（静态链接） | `gateway/gateway-core/src/manager.rs:966-978`（`spawn_south_scheduler`），实际 `poll_group` 调用在 manager.rs:845 | Manager 在**自己的 runtime 内直接 await 插件方法**，插件方法运行于真实 async 上下文 |
| 注册 | `gateway/gateway-server/src/main.rs:55-65` `register_builtin_plugins()` | 新插件各加一行 `mgr.register_south(...)` |
| 动态加载 | `gateway-core` `PluginLoader`（`GATEWAY_PLUGINS_DIR`） | Windows `.dll` / Unix `.so`，与本次改动无耦合 |
| Schema 校验 | Manager 对 `node_create` / `node_setting` 走同一套校验 | 插件给出 `config_schema`（含 `valid.min/max`）即免费获得创建与热改配置的校验 |
| 指标 | 调度器侧已计 `south_poll_err` / `south_poll_timeout` | 插件无需自己埋点，如实返回 `Err` 即可 |

**FFI 运行时契约（本设计的硬约束，实现者必须内化）：**
同一插件代码在两种宿主形态下行为必须一致，而两者的 async 上下文截然不同——
动态加载下每次 FFI 调用 = 独立线程 + 新建 current_thread runtime + 调用结束 runtime 销毁
（ffi.rs:337-342、loader.rs:104-118）；静态链接下插件方法跑在 Manager 的长生命周期 runtime 里
（manager.rs:966-978）。推论：**任何插件方法内 `tokio::spawn` 出去的任务，在动态加载形态下
活不过当次调用**（runtime 一销毁任务即被丢弃），在静态链接形态下却能存活——两种形态行为
分裂。因此凡是需要跨调用存活的常驻活动（连接、收发循环），必须放在**插件自持的 OS 线程 +
专属 Runtime** 上，与宿主的调用 runtime 完全解耦。本期四个驱动中只有 plugin-iec104 需要
此模式（§3.6），其余三个驱动的方法都在单次调用内完成全部网络 I/O，不受此约束。

## 3. 方案

### 3.1 依赖选型（已核实）

核实方式（2026-10-05 执行）：
`cargo search <关键词>`、`cargo info <crate>`、crates.io sparse index（依赖清单）、
crates.io API v1（更新时间/下载量）；对四个最终候选另从 static.crates.io 下载 `.crate` 解包，
核实了内部行为（同步/异步、重连逻辑、对象类型枚举、模拟器）。选型硬标准：**纯 Rust、无 C
原生库依赖（必须）**——工作区要出 Windows `.dll` 与 Linux `.so` 两种 cdylib，且
`docs/SDK与插件开发.md` 的 FFI 契约要求插件与宿主各自静态链接运行时，C 库会让交叉构建与
许可分发都变复杂；**异步为优先项而非硬标准**——同步阻塞 API 的 crate 允许选用，但驱动必须
用 `tokio::task::spawn_blocking`（或专用线程）封装，禁止在 async 上下文直调（本期仅
bacnet-rs 属此类，见 §3.4）；能覆盖读+写。

### 3.2 通用插件骨架（四驱动一致）

目录结构对齐 plugin-modbus-tcp（§2.2），以 `plugin-s7` 为例：

```
gateway/gateway-plugins/plugin-s7/
├── Cargo.toml
└── src/
    ├── lib.rs        # S7Plugin：SouthPlugin 全量实现 + config_schema/tag_schema
    ├── config.rs     # config_str / config_u16 / config_bool 取值 helper（从 modbus-tcp 拷贝）
    ├── address.rs    # S7 地址语法解析（纯逻辑，default feature 下也能编译、能单测）
    ├── state.rs      # per-node 状态 + ConnectionState 指数退避（拷贝 modbus-tcp/state.rs 后按需裁剪）
    ├── value.rs      # 协议值 ↔ DataValue（纯逻辑）
    └── ffi.rs        #[cfg(feature="ffi")] mod ffi; → gateway_sdk::export_south_plugin!(crate::S7Plugin);
```

`Cargo.toml` 统一形状（照抄 `plugin-modbus-tcp/Cargo.toml`）：

```toml
[lib]
crate-type = ["lib", "cdylib"]

[features]
default = ["s7-client"]          # 四个驱动分别是 s7-client / bacnet-client / eip-client / iec104-client
s7-client = ["dep:snap7-client"]
ffi = []

[dependencies]
gateway-sdk = { path = "../../gateway-sdk" }
async-trait = "0.1"
tokio = { version = "1", features = ["rt-multi-thread", "time", "sync", "macros", "net"] }
tracing = "0.1"
serde = { version = "1", features = ["derive"] }
serde_json = "1"
uuid = { version = "1", features = ["v4"] }
snap7-client = { version = "0.1.7", optional = true }
```

与 `plugin-opcua`（default=[]，因 OpenSSL）不同：四个依赖均为纯 Rust，因此客户端 feature
**默认开启**（与 modbus-tcp 一致），构建与 CI 无需额外环境变量。

通用实现约定（实现者必须遵守）：

- **状态**：`struct XxxPlugin { state: Arc<RwLock<HashMap<NodeId, XxxState>>> }`；
  `open` 建状态并返回默认组（`default` 组，`interval_ms: 1000`，照 modbus-tcp lib.rs:113-121），
  `close` 删状态；`start`/`stop` 只打日志或启/停连接；`setting` 原地更新可热改字段
  （host/port 等），**改不动连接参数时直接断开现有连接**让下轮轮询重建。
- **无节点的调用**：`state.get(&node_id)` 失败一律 `PluginError::msg("node not open")`（modbus-tcp lib.rs:562-565）。
- **错误分类**：建连失败用 `connection_failed`，读/写超时用 `timeout`，地址不合法用 `tag_invalid`，
  配置缺失/非法用 `config_invalid`；不要把所有错误都塞进 `msg`。
- **poll_group 返回顺序**：结果数组按入参 `tags` 顺序返回，单点失败时该点回填占位值并在日志中
  说明，整组失败才返回 `Err`（modbus-tcp lib.rs:772-777 的 slots 模式）。
  **唯一例外是 plugin-iec104**：缓存中不存在的 IOA **直接跳过、不回填占位 0**（该点位从未上送过，
  回填 0 会给规则引擎/历史库喂假值），返回条目数可少于入参 tags 数——此例外为有意设计，见 §3.6。
- **Schema**：`config_schema()` 每个参数给 `name_zh/en`、`description_zh/en`，数值型带
  `valid.min/max`；`tag_schema()` 给 `data_types` 与 `address_format_zh/en`；
  `tag_regex` 按 data_type 给正则（UI 校验）。`validate_tag` 调 `address.rs` 的解析函数。
- **禁止跨调用 spawn**：插件方法（open/poll_group/write_tags/…）内不得 `tokio::spawn` 任何
  需要跨调用存活的任务——动态加载形态下每次调用新建 current_thread runtime 且调用结束即销毁
  （§2.1 硬约束，ffi.rs:337-342），spawn 的任务活不过当次调用。需要常驻活动时用「插件自持
  OS 线程 + 专属 Runtime」模式（本期仅 plugin-iec104，见 §3.6）。
- **同步阻塞调用隔离**：在 async 方法内调用阻塞式客户端（本期仅 bacnet-rs）必须包
  `tokio::task::spawn_blocking`，禁止直调阻塞 Manager 的调度 worker（manager.rs:966-978 起
  的采集任务共用 runtime）。

### 3.3 plugin-s7（south-s7）

**协议角色**：客户端（S7Comm 经 COTP/TPKT over TCP:102；S7CommPlus 用于 S7-1200/1500）。
单次调用内完成连接与读写，ConnectionState 退避模式适用（§3.2），无跨调用任务。

**节点配置（config_schema）：**

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `host` | string | `127.0.0.1` | PLC IP |
| `port` | int 1–65535 | `102` | |
| `protocol` | select | `s7comm` | `s7comm`（经典，`S7Client`）/ `s7comm-plus`（`S7PlusClient`，实验性，见 §5） |
| `rack` / `slot` | int 0–15 / 0–31 | `0` / `1` | S7Comm 连接参数 |
| `connection_timeout_ms` | int 1000–60000 | `3000` | |
| `read_timeout_ms` | int 1000–60000 | `3000` | 单次读/写等待上限（插件侧 `tokio::time::timeout` 包一层） |

**地址语法（自研 `address.rs`，映射到 snap7-client 的区域+字节+位；不直接依赖 crate 的 `parse_tag`，
保证 default feature 关闭时解析器仍可编译可单测）：**

| 写法 | 含义 | data_type 映射 |
|---|---|---|
| `DB2.DBX0.1` | DB2 字节 0 位 1 | bool |
| `DB2.DBW10` / `DB2.DBW10#B` | DB2 字 10（#B=小端交换） | int16/uint16 |
| `DB2.DBD12` / `DB2.DBD12#F` | DB2 双字 12；#F=float32，#D=float64 | int32/uint32/float32/float64 |
| `DB1.S20.32` | DB1 字节 20 起长度 32 的字符串 | string |
| `M0.0` / `MB10` / `MW12` / `MD16#F` | Merker 位/字节/字/双字 | 同上 |
| `I0.0` / `IB2` / `IW4` | 过程输入 | bool/int16/uint16 |
| `Q0.0` / `QB2` / `QW4` | 过程输出 | 同上 |
| `DB2.DBB0.N` | bytes，N 为长度 | bytes |

位宽由 `data_type` 决定、`#` 后缀只用于浮点/字节序提示，与 modbus-tcp 的 `4x!addr[.BIT][#ENDIAN]`
风格保持一致。`tag_regex` 按 bool/int16/float32/… 分别给出（参照 modbus-tcp lib.rs:363-384）。

**采集**：`poll_group` 把组内全部点位转成 `MultiReadItem` 一次批量读（S7Comm 单 PDU 天然支持多
item，无需 modbus 式合并规划器）；失败 → `on_failure()` 退避（复用 ConnectionState 模式）。
**写值**：`MultiWriteItem`；bool 写位，数值按 data_type 定宽，string/bytes 按地址中的长度写。
写值走 `Tag.attr ∈ {Write, ReadWrite}` 的点位（`attr` 仅作 UI 提示，插件不强制拦截）。

**测试**：`snap7-server` 0.1.7（同一仓库的官方模拟器）作为 dev-dependency，见 §4.2。

### 3.4 plugin-bacnet（south-bacnet）

**协议角色**：BACnet/IP 客户端（UDP:47808）。

**关键实现约束：bacnet-rs 的 client API 是同步阻塞的**（`BacnetClient::new` / `who_is` /
`read_property` / `write_property` 均为 `pub fn`，内部 std `UdpSocket`，client/mod.rs:180,281,574,604；
解包核实 `src` 内 0 处 `async fn`）。因此：

- 所有对 `BacnetClient` 的调用必须包 `tokio::task::spawn_blocking`（§3.2 约定），客户端对象
  存放在 `Arc<std::sync::Mutex<Option<BacnetClient>>>`，**std Mutex 只允许在 spawn_blocking
  闭包内加锁**，严禁跨 await 持锁。
- `BacnetClient::new()` 默认 5 秒超时（client/mod.rs:179-183 docstring），用其 builder 把
  `timeout_ms` 配置映射进去。
- UDP 无连接，不用 ConnectionState；用**连续失败计数**变体：单次超时只报该轮失败，连续失败
  ≥ 3 次后丢弃客户端（Mutex 置 None），下轮轮询经 spawn_blocking 重建——避免把丢包误判成
  设备离线（对应 §5 R6）。

**节点配置：**

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `ip` | string | `127.0.0.1` | 目标设备 IP |
| `port` | int 1–65535 | `47808` | |
| `device_instance` | int 0–4194303 | 可选 | 目标设备实例号；填了则先 Who-Is 校验设备存在 |
| `timeout_ms` | int 500–60000 | `3000` | 请求超时（映射到 BacnetClient builder） |
| `write_priority` | int 1–16 | `8` | WriteProperty 优先级 |

**地址语法：`<object-type>:<instance>[:<property>]`**

缩写映射**以 bacnet-rs 实际存在的 `ObjectType` 枚举为准**（解包核实
`bacnet-rs-0.3.2/src/object/object_type.rs:7-70`；注意标准缩写 `li`/`lo` 不是独立对象类型——
crate 中仅有 `LargeAnalogValue = 46`，没有 LargeAnalogInput/Output；字符串对象是
`CharacterstringValue = 40`，惯用缩写 `csv`）：

| 地址写法 | ObjectType（枚举值） | 允许的 data_type |
|---|---|---|
| `ai:1` / `analog-input:1` | AnalogInput (0) | float32 / float64 |
| `ao:n` / `av:n` | AnalogOutput (1) / AnalogValue (2) | float32 / float64 |
| `bi:n` / `bo:n` / `bv:n` | BinaryInput (3) / BinaryOutput (4) / BinaryValue (5) | bool |
| `msi:n` / `mso:n` / `msv:n` | MultiStateInput (13) / MultiStateOutput (14) / MultiStateValue (19) | int32 |
| `bsv:n` | BitstringValue (39) | bytes（位串原值） |
| `csv:n` | CharacterstringValue (40) | string |
| `iv:n` | IntegerValue (45) | int32 |
| `lav:n` | LargeAnalogValue (46) | float64 |
| `osv:n` | OctetstringValue (47) | bytes |
| `piv:n` | PositiveIntegerValue (48) | uint64 |

- 省略 property 时默认 `present-value`；`ai:5:units` 之类可读任意属性。
- **本期只开放上表**：其余 ObjectType（Calendar/Device/Schedule 等）由 `validate_tag` 拒绝，
  允许清单写入 `tag_schema`——string 类型的合法地址形式即 `csv:n`。
- data_type 相干性在 `validate_tag` 校验（如 `ai` 配 bool → `tag_invalid`），对照上表实现。

**采集**：每轮 `poll_group` 用一次 **ReadPropertyMultiple** 拉回组内全部点位的 present-value
（bacnet-rs 已确认支持，见 §3.1）；若 crate 的 RPM 接口在批量上限上有问题，回退为逐点
ReadProperty（实现时二选一，接口形状不变）。**写值**：WriteProperty 写 present-value，
优先级取 `write_priority`；写 Null 表示 relinquish 暂不开放，留作参数 `relinquish`（默认关）。

**上游已知限制（如实告知，来自 bacnet-rs 文档）：** 无分段（segmentation）实现 → 超大对象列表
读取会失败；仅 BACnet/IP 无路由；文档自述「under active development, not yet production-ready」。
缓解：§5 的适配层隔离 + 本期只依赖 RP/RPM/WP 三个最成熟的服务。

### 3.5 plugin-ethernet-ip（south-ethernet-ip）

**协议角色**：EtherNet/IP 显式报文客户端（TCP:44818），目标 Allen-Bradley CompactLogix /
ControlLogix（rust-ethernet-ip 的定位即如此）。单次调用内完成连接与读写，ConnectionState
退避模式适用，无跨调用任务。

**节点配置：**

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `host` | string | `127.0.0.1` | PLC IP |
| `port` | int 1–65535 | `44818` | |
| `route_slot` | int 0–255 | 可选 | 经背板路由到指定槽位（`RoutePath::add_slot`），不填为直连 |
| `connection_timeout_ms` | int 1000–60000 | `3000` | |

**地址语法：原样透传 Logix 符号标签路径**（不做二次解析，crate 内有 `TagPath` 解析器）：
`MyTag`、`Program:Main.MotorRunning`、`Array[3]`、`MyUdt member.name`。
`validate_tag` 只校验非空、无空白、无控制字符；语义错误由读/写时返回（crate 报错）。

**写值**：`write_tag` 整体写（UDT 成员可写，整结构数组元素写不支持——crate 已知边界，§5 不列风险，

### 3.6 plugin-iec104（south-iec104）

**协议角色**：主站/控制站（client）。与另外三个驱动**架构不同**，原因有二：
① 104 是常连接 + 自发上送协议，不存在「一轮轮询」概念；② **FFI 运行时契约禁止在插件方法内
spawn 跨调用存活的任务**（§2.1 硬约束：动态加载下每次调用新建 current_thread runtime 且调用
结束即销毁，ffi.rs:337-342；而静态链接下插件方法却运行在 Manager 的长驻 runtime 里，
manager.rs:966-978——如果用「start 里 tokio::spawn 连接任务」的写法，动态加载/进程隔离形态下
连接任务活不过当次调用，PointCache 永远为空，且同一插件两种形态行为不一致）。此外
`iec104::Client::connect` 自身也在**调用方 runtime** 上 `tokio::spawn` 接收任务
（解包核实 iec104-0.5.1/src/client.rs:125-127），所以 Client 必须活在一个长生命周期 runtime 上。

**架构：插件自持 OS 线程 + 专属 tokio Runtime + 点位缓存**

```
open(node):
  cache   = Arc<Mutex<HashMap<IOA, (DataValue, 毫秒时间戳)>>>      # 与插件状态共享
  health  = Arc<AtomicBool> + 连接代次计数                          # on_reconnecting 维护
  (cmd_tx, cmd_rx) = mpsc::channel::<Command>(16)
  # Command = Connect | Disconnect | Write(IoaCmd, oneshot 回执) | Shutdown
  runtime = tokio::runtime::Builder::new_current_thread().enable_all().build()
  join    = std::thread::Builder::new().name("iec104-<node>")
              .spawn(move || runtime.block_on(worker_loop(cache.clone(), health, cmd_rx)))
start(node):  cmd_tx.send(Connect)
stop(node):   cmd_tx.send(Disconnect)          # 保留缓存
close(node):  cmd_tx.send(Shutdown); join.join()   # 线程退出 → runtime 随之销毁

worker_loop（跑在自持线程的 runtime 上，长驻至 Shutdown）:
  Client::new(ClientConfig, Callback{cache, health})
  on Connect:      client.connect()?              # crate 内部 spawn 接收任务并自管重连（见下）
                   → 构造 C_IC_NA_1 总召唤经 send_asdu 下发（client.rs:140）
                   → [可选] select! 定时器驱动周期 GI / 周期时钟同步
  on Write:        send_command_sp / send_command_dp（client.rs:204,248）→ oneshot 回执
  on Disconnect:   client.stop_receiving()（client.rs:181），缓存保留
  on Shutdown:     stop_receiving + return

Callback（ClientCallback，async-trait）:
  on_asdu          → 解码 M_SP/M_DP/M_ST/M_ME_*（含带 CP56 时标变体）→ 写入 cache
  on_reconnecting  → 置 health=断开中，打日志；**不重连**（crate 自管，见下）
  on_error         → 打日志
```

**重连归属（必须二选一，本设计选定前者）：** iec104 crate 内置无限重连——接收出错进入
`Reconnecting` 状态，`make_connection` 失败则 `sleep(t0)` 后重试（解包核实
connection_handler.rs:133-149），并有 `on_reconnecting` 回调（client.rs:52）。**插件层不得再
叠加自己的退避重连**（两层重连会互相竞态：插件侧重建会撞上 crate 侧的半开连接状态）；插件只
通过 `on_reconnecting` / `on_error` 维护健康标志用于诊断。实际重连节拍因此是 crate 固定的
`t0`（默认 10s），不是 modbus 式指数退避——这是有意的取舍，写值失败时按健康标志直接返回
`connection_failed`，不触发重建。

- `poll_group`：只读 cache 快照，**不触网、不等待**；按入参 tags 顺序组装，
  **IOA 未命中直接跳过（§3.2 声明的例外）**并打 debug 日志。
- `write_tags`：经 cmd 信道发 `Write` 命令，在 oneshot 上等待回执（FFI 形态下该等待发生在
  `__gateway_plugin_block_on` 的 current_thread runtime 内，等待 async 信道是合法的）；
  超时用 `t1_ms`；同一时刻只允许一条未完成命令（worker 串行处理）。`Bool` → 单点命令
  `send_command_sp`，`Int` 0..3 → 双点命令 `send_command_dp`，其他类型 `tag_invalid`；
  默认直接执行、不走 select-before-operate。
- 缓存值映射：M_ME_NA/NB（规一化/标度，int16）→ `Int16`，M_ME_NC（短浮点）→ `Float32`，
  M_SP → `Bool`，M_DP → `Bool`（0/1，中间态记 0 并打 warn）。

**节点配置：**

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `host` / `port` | string / int | `127.0.0.1` / `2404` | 被控站地址 |
| `common_address` | int 1–65534 | `1` | 公共地址 CA |
| `originator_address` | int 0–255 | `0` | 源发地址 OA |
| `k` / `w` | int ≥1 | `12` / `8` | APCI 窗口。**硬约束：`w ≤ ⌊2k/3⌋` 且均 > 0**（解包核实 iec104-0.5.1/src/config.rs:60-84 `validate()`，由 `Client::connect` 在打开 TCP 前强制调用，client.rs:108-110）。config_schema 的 `valid.min/max` 无法表达跨字段约束，因此 **open()/setting() 中必须代码校验**，不合法返回 `config_invalid`（消息中带上限值）；Schema 的 description 需写明该约束。默认 12/8 恰好合法（⌊24/3⌋=8） |
| `t0_ms` / `t1_ms` / `t3_ms` | int | `10000` / `15000` / `20000` | 建连（兼 crate 重连间隔）/ 应答 / 测试帧超时（t2 由 k/w 推导，不暴露） |
| `gi_interval_ms` | int ≥0 | `300000` | 周期总召唤，0=仅连上时一次 |
| `clock_sync_interval_ms` | int ≥0 | `0` | 周期时钟同步，0=关闭 |

**地址语法：`IOA` 十进制数字**（1–16777215，`tag_regex` 校验 `^[0-9]{1,8}$` 且解析后 ≤ 16777215）；
data_type 只作展示提示，实际类型由上送 ASDU 决定（缓存写入时按 ASDU 类型转 `DataValue`）。

**测试**：`iec104` crate 自带 server 模块（§3.1 核实），dev 环境起一个本地 104 被控站做回环
集成测试（§4.2）；ASDU→缓存映射、IOA 解析、命令编码、k/w 校验全部纯逻辑单测。

### 3.7 与现有机制的集成方式

1. **静态链接**：4 行 `register_south`（main.rs:60-63 处），插件名 `s7` / `bacnet` /
   `ethernet-ip` / `iec104`（与 crate 名 `plugin-<name>` 对应，风格同 modbus-tcp）。
2. **动态加载 / 进程隔离**：`Cargo.toml` 已按 §3.2 声明 `crate-type=["lib","cdylib"]` 与
   `ffi` feature；`scripts/build-plugins.ps1` / `build-plugins-so.sh` / `package-release.sh`
   按清单增行（§2.3）。进程隔离模式下宿主把每次 FFI 调用放独立线程执行（loader.rs:104-118），
   插件内 `block_on` 安全（ffi.rs:337-342）。
   **但「无需适配」仅对方法内完成全部 I/O 的三个驱动成立**；plugin-iec104 之所以在两种形态下
   行为一致，正是因为其连接线程、专属 runtime 与 iec104 Client 全部自持于插件内、不依赖宿主
   调用 runtime 的存活性（§3.6）——这是该架构存在的理由，不是可选优化。
3. **前端零改动**：Web UI 从 `GET /api/plugins/south` 与 `config_schema`/`tag_schema` 动态生成
   表单与点位校验，无需新增页面；`PluginMeta` 提供中英文名称/描述（plugin.rs:15-28）。
4. **数据链路**：`poll_group` 结果经 Manager 写入 Bus → 北向/历史/规则引擎全部自动生效；
   `read_tags`/`write_tags` API（架构说明 §五）对四个新驱动直接可用。
5. **性能基线**（可选，不阻塞）：`gateway-bench` 如需覆盖新驱动，只需测 `address.rs` 解析与
   `value.rs` 转换（纯函数），不引入网络依赖。

## 4. 测试策略

### 4.1 分层原则

本环境（Windows 11 / rustc 1.99.0）**没有任何一台目标真机**（S7 PLC、AB Logix PLC、BACnet
现场设备、104 RTU 均不可达）。因此：

- **默认跑的（CI/`cargo test` 全量）**：只有纯逻辑单测——地址解析、值编解码、配置解析、
  退避/失败计数状态机、104 的 ASDU→缓存映射与命令编码及 k/w 校验、EIP 的 PlcValue 映射。
  全部内联 `#[cfg(test)] mod tests`（对齐 modbus-tcp 的组织，§2.2）。
- **标记 `#[ignore]` 的（本地手动 / 有模拟器时）**：走真实 TCP/UDP 端口的回环集成测试。
- **本环境完全无法验证的**：真机行为（见 4.3 表末行），如实标注，不假装可行。

### 4.2 各驱动测试矩阵

| 驱动 | 纯逻辑单测（必做） | 本地「真实服务」回环集成测试（`#[ignore]`） | 真机 |
|---|---|---|---|
| plugin-s7 | 地址语法全表（§3.3 每种写法 × data_type 定宽 × `#F/#D/#B` 后缀 + 非法样例）；位宽/字节序转换；配置解析；ConnectionState 退避 | **可以做**：dev-dependency `snap7-server` 0.1.7（rs-snap7 仓库的官方模拟器，纯 Rust 库）起在 `127.0.0.1:0`，写入初值 → 用插件 `poll_group` 读回断言；写值回读断言 | ❌ 无真机，标注待现场 |
| plugin-ethernet-ip | PlcValue↔DataValue 映射全表；tag path 合法性校验；配置解析；退避 | **可以做（v2 修正：此前误判为无模拟器）**：所选 crate 自带完整 CIP 显式报文服务端 `rust-ethernet-ip-1.2.1/src/bin/plc_sim.rs`（解包核实：647 行；支持 RegisterSession 0x65 / SendRRData 0x6F / Read Tag 0x4C / Write Tag 0x4D / Multiple Service Packet 0x0A，内置 Bool/Dint/Real/String/UDT/Array 标签值；绑定 `127.0.0.1:0` 并在 stdout 打印实际地址，plc_sim.rs:9-11,45-48）。它是 **bin 而非库 API**（依赖的 bin 不会随 dev-dependency 构建），集成测试采用「照抄其应答器核心（约 200 行，MIT 许可，注明来源文件与行号）到 plugin-ethernet-ip 测试模块」的方式，或本地一次性 `cargo install rust-ethernet-ip --bin plc_sim` 后以子进程拉起、解析 stdout 获得端口——实现者二选一，回环覆盖 读/写/批量 三条路径 | ❌ 无真机（模拟器验证报文级正确性；UDT/路由等真机特性待现场，见 R3） |
| plugin-bacnet | 类型缩写解析（§3.4 全表 + 非法/越界样例）+ property 省略 + validate 相干性；DataValue 映射；失败计数重建 | **尽力而为**：dev-dependency `mabi-bacnet` 1.7.1 模拟器起在 `127.0.0.1:0`；若模拟器与 bacnet-rs 报文兼容性不足（模拟器保真度未核实，是本表唯一未验证项），降级为「手写最小 UDP 应答器 + bacnet-rs 编码器构造请求」做单请求回环，并注明覆盖有限 | ❌ 无真机 |
| plugin-iec104 | IOA 解析/边界（1、16777215、越界）；ASDU→缓存映射表（M_SP/M_DP/M_ME_NA/NB/NC 及带时标变体）；命令编码（sp/dp）；k/w 约束校验（含 w>⌊2k/3⌋、k=0、w=0）；缓存快照与 IOA 未命中跳过；open/setting 配置校验 | **可以做**：`iec104` crate 自带 server 模块（client/server 同 crate 同版本，无循环依赖问题；若其 server 模块在 default feature 下不可达，则手写最小 I 格式帧应答器覆盖 STARTDT+GI+数据帧），验证 Connect→GI 拉数→缓存出现→`poll_group` 读回→下发单点命令→Stop 后缓存保留→close 线程退出（join 成功、无残留线程） | ❌ 无真机 |

补充约束：
- 四驱动的 default feature（客户端依赖）必须保证 `cargo test -p plugin-<name>` 在无网环境可跑
  （依赖经 `cargo info` 已可拉取，Vendor 化不是本期范围）。
- `#[cfg(not(feature = "<proto>-client"))]` 的降级分支（返回占位值/NotSupported）照 modbus-tcp
  lib.rs:781-790 的写法保留，编译两边都过（CI 用 `cargo clippy -D warnings` 全 feature 检查）。
- 回环测试与纯逻辑测试**不得互相依赖**；`--ignored` 测试崩溃不得影响默认测试结果。
- IEC104 回环测试必须额外断言「回环测试结束后无残留 worker 线程」——自持线程模式的退出正确性
  只能在这里验证（§5 R5）。

### 4.3 验收口径

| 验证层级 | 能否在当前环境完成 | 说明 |
|---|---|---|
| 编译（lib + cdylib 双形态、四驱动 × 开/关 client feature） | ✅ | `cargo build -p plugin-<x> --features ffi` |

## 5. 风险与回退

| # | 风险 | 影响 | 缓解 / 回退 |
|---|---|---|---|
| R1 | S7 两个候选 crate 都很年轻（下载量均 <2k，docs 覆盖率 35–50%） | snap7-client API 与边界行为可能与文档有出入 | **回退路径**：驱动内部把 crate 调用收敛在 `client.rs` 适配模块（open/read/write 三个函数），可整体替换为 `tokio-s7`（仅 S7Comm）或 `turbos7` 而不动 `SouthPlugin` 层；S7CommPlus 相关代码单独 `mod plus`，出问题时砍掉只留 S7Comm |
| R2 | bacnet-rs 自述未达 production-ready、无分段，且 client 为同步阻塞 API | 大对象列表读取失败；封装不当会阻塞调度 worker | 本期只依赖 Who-Is/RP/RPM/WP；批量读做「RPM 失败 → 逐点 RP」兜底；**全部调用强制走 spawn_blocking（§3.4，含单测断言不持锁跨 await 的代码评审项）**；适配层隔离，必要时换 crate（成本最高，见 §6 步骤排序把它放最后） |
| R3 | rust-ethernet-ip 对真机 PLC 的兼容性（尤其 UDT/背板路由）本地无法验证 | 模拟器只能证明报文级正确性 | 本地回环已可行（plc_sim，§4.2）；真机专项（RoutePath、UDT、fragmented read）留现场验收清单；crate 回退候选 rseip（陈旧，仅救急） |
| R4 | iec104 crate API 仍在演进（README 自述），edition 2024 | 版本升级可能 break；CI 工具链需 ≥1.85 | Cargo.toml 锁 `=0.5.1` 精确版本，升级走单独 PR；ASDU→缓存映射与命令编码自研在 value.rs/command.rs，协议升级只影响薄薄的连接层（worker.rs） |
| R5 | IEC104 自持线程/Runtime 的生命周期错误（泄漏、双重关闭、close 未 join） | 线程残留后台重连、退出卡死 | 生命周期集中在一个 `worker.rs`：`close` 先发 `Shutdown` 再 `join`；`stop` 仅 `Disconnect` 保留线程与缓存，`start` 复用同一线程；回环测试断言线程退出（§4.2）；重连归 crate（connection_handler.rs:133-149，固定 t0），插件不叠加退避，避免双重重连竞态 |
| R6 | UDP（BACnet）丢包被误判为设备离线 | 状态抖动 | 连续 N 次失败才重建客户端（§3.4），单次超时只报该轮失败；不设 UDP「连接」概念 |
| R7 | 写值误操作（遥控/写 PLC） | 生产事故 | 写入口保留 `Tag.attr` 校验与 `not_supported` 明确报错；遥控默认直执行不走 select-before-operate，文档中显式声明，后续按需加参数 |
| R8 | 四驱动代码复制导致漂移 | 后续修 bug 要改四处 | config.rs/ConnectionState 允许拷贝（现状 modbus-rtu 也如此）；禁止从 gateway-sdk 之外引共享依赖，避免本期扩大改动面 |
| R9 | IEC104 两种宿主形态行为不一致（评审一曾命中的架构缺陷） | 动态加载形态下 PointCache 恒空、写值失效 | 已通过 §3.6 自持线程架构消除；§2.1 硬约束与 §3.2「禁止跨调用 spawn」约定防止同类问题复发，代码评审按此两条检查 |

**整体回退**：四个插件彼此独立、互不依赖；任何一个出问题可单独从 workspace members 与
`register_builtin_plugins` 移除，不影响其余插件与核心。

## 6. 分步实施顺序

> 原则：先立骨架（驱动 1 建立通用骨架与测试范式，后三个复制）→ 按风险从低到高、按「本地可验证
> 程度」从高到低排序；每步结束都在 CI（fmt/clippy/test/build）绿灯后才进下一步。

| 步骤 | 功能项 | 交付内容 | 验收 |
|---|---|---|---|
| 1 | `south-s7` | `plugin-s7` 全量（S7Comm 主路径 + S7CommPlus 实验开关）+ `snap7-server` 模拟器 `#[ignore]` 集成测试；同步改 §2.3 清单的全部 5 处——**这一步确立其余三个驱动复制的骨架** | 默认单测 + `--ignored` 模拟器测试绿 |
| 2 | `south-iec104` | `plugin-iec104`（自持线程 + 缓存架构，§3.6；重连归 crate）+ 本地 104 server 回环测试（含线程退出断言）；k/w 校验单测 | 默认单测 + 回环测试绿 |
| 3 | `south-ethernet-ip` | `plugin-ethernet-ip`（透传标签 + BatchOperation）+ plc_sim 回环集成测试（照抄应答器或子进程方式，§4.2）；现场验收清单 | 默认单测 + `--ignored` 回环测试绿；真机项标注待现场 |
| 4 | `south-bacnet` | `plugin-bacnet`（spawn_blocking 封装 + RPM 批量 + 逐点兜底 + Who-Is 校验）+ mabi-bacnet 回环（尽力而为）；最后实施以便吸收 bacnet-rs 上游变化 | 默认单测绿；回环按实际兼容性留档 |
| 5 | 收尾 | `docs/功能实现清单.md` §二对应行改 ✅（注明「真机验收待现场」）；（可选）gateway-bench 增加地址解析基准 | 全量 `cargo test` / `clippy -D warnings` / `fmt --check` 绿 |
