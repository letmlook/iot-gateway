## 1. 定位与范围

流程编排把「采集 → 处理 → 告警/上报」从单点流水线（rules + filters）升级为**可声明的 DAG**：

```
south group 数据 → [处理算子 DAG] → 多路输出（北向插件 / 告警事件 / 历史标记 / 总线再发布）
```

**MVP 范围（M1-①②）**：
- 流程数据模型 + 校验 + 执行引擎（顺序与并行分支，无环）；
- MVP 算子集：`source`（南向组）、`threshold_alarm`、`state_change_alarm`、`route`（单条件双输出）、`sink_north`、`sink_alarm`；
- 告警事件表 + 生命周期（active → acknowledged → resolved）+ REST + WS 通道；
- Flow CRUD API（draft / published 两态）+ 前端 FlowEditor + 告警中心页。

**明确不做（MVP）**：rhai/python 脚本算子（沙箱风险，redesign 曾被迫加固 `59e88c6`，延后专项）、
flow→flow 级联（M1 构造性禁环，见 §3.4）、分布式执行、动态图热更新（改图 = 重新部署）。

## 2. 数据模型

沿用 redesign/v1 已验证的骨架，按多租户与现行模式修订。

### 2.1 核心类型

```rust
pub enum FlowStatus { Draft, Published }        // 仅两态；运行态由运行时派生（见 §3.3）
pub enum NodeKind { Source, Operator, Sink }    // 南向源 / 处理 / 输出端
pub enum AlarmLevel { Critical, High, Medium, Low, Info }

pub struct Flow {
    pub id: Uuid,
    pub tenant_id: String,            // 多租户：创建时归属，所有查询走租户过滤
    pub name: String,                 // 同租户内唯一
    pub description: Option<String>,
    pub status: FlowStatus,
    pub version: i64,                 // 每次 publish 递增
    pub graph: FlowGraph,             // 见下；单 JSON 文档存储（含 position，见 §7-P4）
    pub created_at / updated_at: DateTime<Utc>,
}

pub struct FlowGraph {
    pub nodes: Vec<FlowNode>,         // {id, name, kind, operator: Option<String>, config, position:{x,y}}
    pub edges: Vec<FlowEdge>,         // {source_node_id, source_port, target_node_id}
}
```

与 redesign/v1 的差异（及理由）：

| 项 | redesign/v1 | v2 | 理由 |
|---|---|---|---|
| 状态机 | draft/deployed/running/paused/stopped/error 六态入库 | **draft/published 两态入库**，running/error 由 FlowRuntime 派生不入库 | 运行态是运行时事实，入库即产生「重启后状态陈旧」问题（与节点 Stopped/Running 教训同源） |
| 位置 | `NodePosition` 字段 + **独立列迁移**（两次 commit 才修对） | position 只存在于 graph JSON，**无独立列** | 单文档存储，编辑器整图保存，无列迁移 |
| 端口类型 | Port{id,name,type:Data/Control,required} | MVP 仅 `source_port` 命名（alarm 双输出：`alarm`/`normal`），不做类型系统 | 类型检查的收益在 MVP 算子集下可由校验器穷举替代 |
| 失败策略 | FlowFailurePolicy 内联绑定 | 订阅侧执行天然隔离（§3.1），失败记指标 + 事件日志 | 无热路径耦合则无需 fail_open/closed 语义 |
| 租户 | 无 | `tenant_id` 列 + 查询过滤 + 历史告警冗余落列（与 samples 表同法） | 形态 B 已上线，新表必须带租户 |

### 2.2 SQLite 模式（`flows` / `alarm_events`，schema v3）

```sql
CREATE TABLE flows (
  id TEXT PRIMARY KEY, tenant_id TEXT NOT NULL,
  name TEXT NOT NULL, description TEXT,
  status TEXT NOT NULL,               -- draft | published
  version INTEGER NOT NULL,
  graph_json TEXT NOT NULL,           -- 单文档：nodes+edges+position
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  UNIQUE(tenant_id, name)
);

CREATE TABLE alarm_events (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,            -- 写入时从流程归属解析（与 samples 冗余落列同法）
  flow_id TEXT NOT NULL, node_name TEXT NOT NULL,
  level TEXT NOT NULL,                -- critical|high|medium|low|info
  state TEXT NOT NULL,                -- active | acknowledged | resolved
  tag TEXT, value REAL, threshold REAL, message TEXT,
  first_ts INTEGER NOT NULL,          -- 首次触发
  last_ts INTEGER NOT NULL,           -- 最近一次命中（去重窗口内前移）
  acked_by TEXT, acked_at INTEGER, resolved_at INTEGER
);
CREATE INDEX idx_alarm_open ON alarm_events(tenant_id, state, first_ts DESC);
```

**告警去重**：同一 (flow_id, node_name, tag, level) 的 `active` 事件存在时，新命中只前移
`last_ts` 并累加计数，不建新行（redesign AlarmStore 的 duplicate-suppression 语义保留）。

## 3. 执行语义

### 3.1 执行位置：总线订阅侧（推荐）vs 数据路径内联

| 方案 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **A 订阅侧（推荐）** | 每个已发布流程 = 一个消费任务（复用北向节点消费模式 `manager.rs` 北向 task 范式），经 SubscriptionTable 订阅 (node,group)；输出端直接调用目标（北向插件 `on_group_data` / 告警存储 / 历史标记） | **零热路径耦合**（poll 预算不受影响，调度器评估结论不破坏）；故障隔离（流程 panic 不影响采集）；无需 fail_open/closed 语义 | 输出延迟多一跳（广播通道 ~µs 级，Q5 基线下不可测）；流程输出如需被其他订阅者看到需再发布（M1 禁止，§3.4） |
| B 内联（redesign 方案） | FlowBinding 插入 `poll_group_once` 过滤链，publish 前执行 DAG | 输出即总线数据，其他订阅者可见 | 采集热路径被用户代码耦合，超时/panic 需 fail_open/closed 语义与隔离壳；与「每节点单 task + 固定节拍」的调度模型冲突 |

**决策建议：A**。redesign 的内联方案是为「流程输出替代原始数据进总线」设计的；v2 MVP 的输出端
（告警/北向/历史）都不需要这个性质，方案 A 用既有 task 模式即可承载，且与进程隔离哲学一致。
B 作为「流程输出接管总线数据」需求的后续演进项保留。

### 3.2 执行引擎

- 拓扑与分层：petgraph toposort + 层内并行（redesign `DagExecutor::execution_tiers` 语义直接采用，含环检测）；
- 每流程一个 tokio task（消费订阅数据 → 按层求值 → 端点投递），**无共享调度器**（调度器评估结论适用）；
- 背压：消费端沿用 `try_publish` 非阻塞语义（缺陷①教训），流程内部队列有界，满则丢弃计数（`flow_dropped_msgs` 指标）；
- 运行态：publish 时启动 task，撤稿/删流程/改图重新部署时停旧起新；网关重启后 published 流程自动恢复（与节点 Running 恢复同法）；
- 状态不落盘：窗口/去重基线重启清零（与 filters/rules 运行态语义一致）。

### 3.3 部署生命周期

```
draft --publish--> published(version+1, 启动 task) --update(改图)--> 自动重建 task
published --unpublish--> draft（停 task；告警事件保留）
```

- 校验只在 publish 时强制（环、孤立节点、source 缺失、sink 缺失、配置 schema 校验——
  复用 `config_schema`/`validate_config` 机制）；draft 保存允许不完整图（§7-P2）。

### 3.4 环的构造性排除（M1）

- 流程输入只允许订阅**南向节点组**；流程再发布（若做）的数据打 `source=flow:<id>` 标记，
  流程订阅查询过滤该来源 → flow→flow 级联与环在构造上不可能，无运行时环检测负担。
- 级联需求出现时再放开（届时仅需移除过滤 + 补环检测），MVP 不实现。

## 4. 告警子系统（M1-②）

### 4.1 算子语义（沿用 redesign `operators/alarm.rs`，裁剪）

- `threshold_alarm`：tag + high/low + level + message（redesign 同款）；
- `state_change_alarm`：tag + from(`*`=任意) → to + level（redesign 同款）；
- `rate_of_change`：**MVP 不做**（需要速度窗口，与「状态不落盘」叠加后语义易错，专项再上）；
- 双端口输出：命中 → `alarm` 端口（→ sink_alarm 落库 + 可选继续接 sink_north），未命中 → `normal` 端口。

### 4.2 生命周期与 API

- 状态机：`active → acknowledged → resolved`（ack 不可重复、resolved 终态；redesign AlarmEvents 规格同款）；
- REST（挂 `/api` 裸路径，**不过 v1 别名**，与路由表现行契约一致；角色：Viewer 读 / Operator ack / Admin resolve+删）：
  - `GET /alarms?state=&level=&page=&page_size=`（分页，租户过滤）
  - `POST /alarms/:id/ack`、`POST /alarms/:id/resolve`
- WS：复用 ws.rs 增 `alarm` 帧类型（机会式推送，REST 轮询为可靠来源——redesign 规格结论沿用）；
- 前端：`/monitor/alarms` 告警中心页（级别 chips 过滤 + ack/resolve 按钮），随 FlowEditor 一起在 M1-③④ 交付。

## 5. API 面（Flow CRUD）

| 端点 | 语义 | 角色 |
|---|---|---|
| `GET /flows`、`GET /flows/:id` | 列表/详情（租户过滤） | Viewer |
| `POST /flows`、`PUT /flows/:id` | 创建/保存草稿（**必须完整往返 nodes+edges**，§7-P1） | Operator |
| `POST /flows/:id/publish`、`POST /flows/:id/unpublish` | 部署/下线（publish 时强制校验） | Admin |
| `DELETE /flows/:id` | 删除（published 先自动 unpublish） | Admin |
| `GET /flows/operators` | 算子发现（名称/schema，供编辑器面板） | Viewer |

- 全部走认证中间件 + 租户过滤（`resolve_node` 同款收口）+ 审计落库（T7 模式）；
- OpenAPI 注解同步（`web` 的 `gen:api` 链路）；
- **不引入 `/api/v2`**（T3 版本化拍板前，新端点按现行「裸路径 + 分页端点可选 v1」契约）。

## 8. 测试计划

1. **单元**：toposort/分层/环检测、校验器（source/sink/config）、告警去重与生命周期状态机、graph_json 往返；
2. **引擎集成**：sim 节点 → 订阅侧流程 → sink_north 直投 + sink_alarm 落库（真插件断言）；
   流程 panic 隔离（杀流程任务不影响采集与北向）；有界队列丢弃计数；
3. **API 面回归**：CRUD 往返（P1）、租户隔离（跨租户 404）、角色矩阵、publish 校验失败路径；
4. **E2E**：Docker 真机（联调记录 §3.1 环境复用）：sim → flow(threshold) → 告警页可见 + mqtt 北向收到处理结果；
