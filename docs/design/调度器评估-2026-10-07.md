# 调度器评估：是否需要「共享 interval 的限并发调度器」（2026-10-07）

## 决策

**暂不需要实现共享 interval 的限并发调度器。** 这是评估决策项，本次未做任何实现。

依据（详见下文）：§15.2 的前提已过时——调度器早已从「每组一个 task」重构为「每运行中南向节点一个 task + 固定节拍 + 全局并发信号量」；在 Q5 规模（200 设备 / 10000 点位）下，该形态的内存开销约 0.6 MB（≈3 KB/task）、调度唤醒 200~2300 次/s（对比总线 21 万+ msg/s 可忽略）、节拍滞后上界由 Windows 计时器量化（15.6 ms）而非 task 架构决定，且饱和场景已有 `south_poll_overrun` 指标可观测。实测中真正值得处理的是**计时器分辨率**这一正交问题（与调度器形态无关，见「附带的正交发现」）。

## 1. 背景与代码事实

`docs/review/优化方案总览-2026-09-26.md` §15.2（第 493 行）原文：

> | 共享 interval 的限并发调度器 | 未做 | 当前"每组一个 tokio task"在千级组时 task 数偏多；建议与压测基线一起评估是否需要 |

**该前提已过时。** 当前实现（`gateway/gateway-core/src/manager.rs`）：

| 事实 | 位置 |
|---|---|
| 每个运行中的南向节点只 spawn **一个**调度 task（注释明言「而不是每个组一个：千级组不再对应千个长驻 task」） | manager.rs:991-1021 |
| 固定节拍：`next_due = now + interval`，不因采集耗时后移 | manager.rs:1090-1092 |
| 空闲等待：睡到最早到期组，上限 `IDLE_MAX = 200ms`，保证新组/取消信号及时感知 | manager.rs:1046-1048, 1074-1087 |
| 到期组逐个取**全局**信号量 permit 后 spawn 进 JoinSet 并发采集 | manager.rs:1098-1124 |
| 全局并发上限 `DEFAULT_MAX_CONCURRENT_POLLS = 32`，由 `GATEWAY_MAX_CONCURRENT_POLLS` 环境变量可调 | manager.rs:46, 89-100；gateway-server/src/config.rs:412-416 |
| 超期观测：一批耗时超过批内最小周期即计 `south_poll_overrun` | manager.rs:1141-1144 |
| 单次采集超时：`3 × interval`（下限 5s），慢设备不挂住调度 | manager.rs:1167 |
| 每拍从 Store 重读组集合，新增/删除组即时生效 | manager.rs:1051-1058 |

Q5 规模下的 task 账本：长驻 task = 每运行中南向节点 1 个（调度）+ 每北向节点 1~N 个（消费与分区转发，manager.rs:380-462）；每拍到期的组各自 spawn 一个**短生命周期** JoinSet task，采完即回收。200 节点 → 长驻约 200 个，短驻峰值 ≤ 全局并发上限 32 + 等待 permit 的排队数量。

## 3. 调度器形态微实验（评估专用，运行后已删除，未入库）

在 `gateway-core` 下临时写了一个形态等价实验（逐行复刻 `south_scheduler_loop` 的固定节拍、`IDLE_MAX` 空闲睡眠、串行取全局 permit、JoinSet 等全批、超期计数），跑了以下场景后**即删除**（git 树已确认无残留）。环境：windows x86_64、rustc 1.99.0、tokio 1.49.0、36 逻辑核、profile=release。

### 3.1 内存：200 个长驻调度 task ≈ +0.6 MB

外部 PowerShell 以 200ms 周期采样进程 WorkingSet（对齐进程相对时刻）：

| 阶段 | WorkingSet |
|---|---:|
| runtime 就绪、未 spawn 调度 task（基线，稳定 8 个采样） | 5.34 MB |
| spawn 200 个调度 task 运行中（10s，含每拍 JoinSet 短驻 task 往返） | 5.92 → 5.96 MB |
| task 结束后 | 5.83 MB |

**增量 ≈ 0.6 MB，≈ 3 KB/节点 task**（含其状态 HashMap 与短驻 task  churn 的页级噪声，Windows 4KB 页粒度）。即使按 Q5 的 100 倍（2 万节点）线性外推也只有约 60 MB，内存不构成约束。

### 3.2 节拍精度与吞吐：Q5 形态全绿

| 场景 | polls/s（需求） | 超限次数 | 节拍滞后 avg / max |
|---|---:|---:|---|
| A：Q5 基准（200 节点 × 1 组 @1000ms，poll 5ms），10s | 200（200） | **0** | 9.0 ms / 15.4 ms |
| B：千级组（200 节点 × 5 组 @200~1000ms，poll 5ms），10s | 2056（2283） | 680（占 tick 4.4%） | 47.9 ms / 300 ms |
| B + 高精度计时器（`timeBeginPeriod(1)`） | 2300（2283） | 21（全部集中在首秒对齐启动波，其后 0） | 3.1 ms / 76 ms |
| A + 高精度计时器 | 200（200） | **0** | 1.9 ms / 3.1 ms |
| 最坏对齐单波：200 节点同刻到期、poll 5ms（32 permit 排队） | — | — | 首波延迟 110 ms；高精度下 47 ms |
| 最坏对齐单波：同上、poll 50ms | — | — | 首波延迟 442 ms（理论 200×62.4/32≈390 ms） |

要点：

1. **Q5 基准形态（每节点 1 组 @1s）零超限**：200 次/s 唤醒、poll 需求仅为 32 permit 容量的 10%，滞后上界完全由计时器量化决定（见 3.3），与「每节点一个 task」无关。
2. **千级组饱和是需求>容量问题，不是 task 数问题**：1000 组 × 平均 600ms 间隔 = 2283 polls/s 需求；计时器量化把每次 5ms 的 poll 拉长到 15.6ms，容量被钳在 32÷15.6ms ≈ 2051 polls/s（实测 2056），于是积压、超限 4.4%。打开高精度计时器后同样 1000 组全速跑满 2300 polls/s、稳态零超限——**同一 task 架构，仅改计时器分辨率，结论反转**。共享 interval 调度器不增加任何设备侧容量，解决不了这一类饱和；`south_poll_overrun` 已把这类饱和如实暴露。
3. **最坏对齐波代价一次性、有界**：即便 200 节点同毫秒到期（真实启动路径 manager.rs:539 循环内连续 spawn，确实近似对齐），5ms poll 下尾部节点 permit 等待 ≤110ms；固定节拍设计（`next_due = now + interval`）保证这不会级联放大。

### 3.3 附带的正交发现：Windows 计时器量化 15.6ms

同机实测（tokio 1.49.0，其源码经检索不含 `timeBeginPeriod` 调用）：

| 请求 sleep | 实测 avg |
|---:|---:|
| 1ms | 15.6 ms |
| 2ms | 15.6 ms |
| 5ms | 15.6 ms |
| 10ms | 15.6 ms |
| 50ms | 62.4 ms |

即本机（Windows）默认 15.6ms 计时器中断周期下，**进程内一切 sleep 型等待都被量化到 ~15.6ms**。对采集的影响：200ms 间隔的组实际周期 ≈ 216ms（+8%）；子 15ms 的 poll 时长全部按 15.6ms 计入 permit 占用（3.2 节场景 B 饱和的直接原因）。这是环境/依赖层问题，与调度器形态无关，且修法便宜（进程启动时调用 `timeBeginPeriod(1)`，或部署 Linux/Docker——Linux 无此量化）。**建议作为独立小项拍板**，先于任何调度器改造；本评估未实现它。

## 4. 推理与决策

对照「每节点一个 task」可能构成问题的三个维度：

| 维度 | Q5 实测 | 判断 |
|---|---|---|
| 内存 | 200 task ≈ 0.6 MB（3 KB/task），外推 2 万节点 ≈ 60 MB | 不构成问题 |
| 调度开销 | 稳态唤醒 200 次/s（Q5 基准）~2300 polls/s（千级组），tokio 多线程 runtime 轻松承载；对比总线 21 万+ msg/s | 不构成问题 |
| 节拍精度 | 滞后上界 = 计时器量化 15.6ms（高精度下 3ms）；对齐启动最坏一次性 +110ms 且不级联 | 瓶颈在 OS 计时器，不在 task 架构；共享 interval 调度器对三个数字都无改善 |

共享 interval 调度器的理论收益是「把 N 个节点的 timer 归并成一个，减少 task 数与唤醒次数」。Q5 数据表明两项资源占用都比可观测阈值低两个数量级以上；而它要付出的代价是真实的：动态变组（每拍重读组集合）需改为共享堆上的下一到期堆/时间轮、节点级取消语义复杂化、单节点慢批（超时 3×interval）会拖住共享轮里其他节拍——换来的是 Q5 下不可测的收益。**决策：暂不需要。**

同时明确：现状架构在 Q5 之外也留有余量——饱和行为由「需求 vs 32 permit 容量」决定，且 `south_poll_overrun`、`south_poll_timeout` 已提供可观测性，不需要为架构预先扩容。

## 5. 复评触发条件（满足其一即重启本评估）

1. **规模**：南向运行节点 ≥ 2000，或全局限并发上限被迫调到 > 128 以容纳采集需求（先按 3.2 的容量公式估算：`节点数 × 组频率 × poll 耗时 ≤ permits × 1s`，按 50% 占用预算规划）。
2. **周期**：出现 < 100ms 的采集周期需求（Windows 量化 + 唤醒开销开始显著；先落地高精度计时器修复再复评，勿直接上共享调度器）。
3. **单节点扇出**：单节点组数 ≥ 100（该节点调度循环内的串行 permit 获取与等全批 JoinSet 成为节点内延迟源）。
4. **观测信号**：非饱和负载下 `south_poll_overrun` 持续增长，或新增的滞后分布指标显示 P99 滞后 > 周期的 10%。
5. **平台**：部署目标固化到 Linux 后重测 3.2/3.3（量化消失，各项阈值需以 Linux 数据重新校准）。
