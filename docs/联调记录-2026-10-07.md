## 3. 复现步骤（完整命令清单）

### 3.1 拉起被测服务


### 4.2 plugin-http ↔ wiremock（HTTP echo）—— ❌ 未通过（缺陷①）

**容器**：`iotgw-itest-http-echo`（wiremock/wiremock:latest，主机 18831）。已预建 catch-all 映射：`POST /hook/* → 200 {"ok":true,"received":true}`。

**环境有效性验证**（手工 curl 自测，与网关无关）：

```console
$ curl -s -X POST http://127.0.0.1:18831/hook/selftest -d '{"probe":"wiremock-ready"}'
{"ok":true,"received":true}
$ curl -s http://127.0.0.1:18831/__admin/requests | python -c "... count POST /hook/* ..."
total /hook/* requests: 1   ← 仅手工 selftest 一条
```

**网关侧现象**：nb-http 节点 running，sim 数据持续产生，但 echo 侧 Journal 中**网关 POST 数为 0**（联调窗口约 20 分钟，覆盖全部 `/hook/*` 请求只有手工那条）。节点连接状态两次采样：

```json
{"connected":false,"dropped_no_client":0,"dropped_rejected":0,"last_error":null,"queue_len":26,...}   // 启动后 ~20s
{"connected":false,...,"queue_len":368,...}                                                            // ~20min 后
```

数据全部积压进离线队列且持续增长，从未发送。

**根因（缺陷①）**：见 §5.1。

**结论**：**未通过**——新节点数据永远到不了 echo 服务。容器侧契约（POST→200）验证无问题。

### 4.3 plugin-influxdb ↔ influxdb:2 —— ❌ 未通过（缺陷①）

**容器**：`iotgw-itest-influxdb`（influxdb:2，实际版本 v2.9.1，`DOCKER_INFLUXDB_INIT_MODE=setup` 自动初始化 org=itest / bucket=gateway / 固定 token）。

**环境有效性验证**（手工行协议写入，与网关无关）：

```console
$ curl -s -X POST "http://127.0.0.1:18832/api/v2/write?org=itest&bucket=gateway&precision=ms" \
    -H "Authorization: Token 0123...cdef" \
    -d "manual_probe,node=sim-itest,group=default temperature=42.0,humidity=60.0 1791361639771"
HTTP 204
$ flux 查询 manual_probe → temperature=42.0, humidity=60.0 两行返回
```

**网关侧现象**：nb-influx 节点 open 日志正常（`open influxdb: http://127.0.0.1:18832/api/v2/write?org=itest&bucket=gateway`），但：

```json
{"connected":false,"last_error":null,"queue_len":166,...}   // ~8min
{"connected":false,"last_error":null,"queue_len":368,...}   // ~20min
$ flux: from(bucket:"gateway") |> range(start:-15m) |> count()   → 空（0 点）
```

InfluxDB 里查不到任何网关写入的点。

**根因（缺陷①）**：见 §5.1。

**结论**：**未通过**——写入端点契约本身可用（手工验证 204/查询正常），但插件数据从不发出。

### 4.4 plugin-tdengine ↔ tdengine/tdengine:3.3.2.0 —— ❌ 未通过（缺陷① + ② + ③）

**容器**：`iotgw-itest-tdengine`（taosAdapter REST 主机 16041，Basic root/taosdata）。

**环境有效性验证**：

```console
$ curl -s -u root:taosdata -d "SHOW DATABASES" http://127.0.0.1:16041/rest/sql
{"code":0,...,"data":[["information_schema"],["performance_schema"],["log"]],"rows":3}
```

**现象 A（缺陷②）**：`auto_create_db=true`，网关日志显示建库「成功」：

```console
INFO ... open tdengine: http://127.0.0.1:16041 database=gateway
INFO ... tdengine database 'gateway' ensured
INFO ... tdengine server_version: {"code":9728,"desc":"unrecognized token: \"{\"sql\":\"SELECT server_version()\"}\""}
```

但服务端 `SHOW gateway.STABLES` → `{"code":904,"desc":"Database not exist"}`。
原因：插件向 `/rest/sql` 发送 JSON 信封体 `{"sql":"..."}`（plugin-tdengine/src/lib.rs:207-208），而 TDengine 3.x taosAdapter 期望**裸 SQL 字符串**；taosAdapter 把整个 JSON 当 SQL 执行，报 9728。响应 HTTP 状态仍是 200，插件只检查 HTTP 状态码（lib.rs:211-213），把 SQL 级失败误判为「ensured」。

**现象 B（缺陷③）**：手工以裸 SQL 建库后，用插件同款写入契约探测：

```console
$ curl -s -u root:taosdata -X POST "http://127.0.0.1:16041/influxdb/v1/write?db=gateway&precision=ms&table_name_key=gateway_table" \
    --data-binary 'sim-itest,node=sim-itest,group=default,gateway_table=sim-itest_default temperature=24.5,humidity=42.5 1791362000000'
{"code":9728,"desc":"syntax error near \"-itest_default\""}     ← measurement 名含 '-'（来自 node_name "sim-itest"）
$ 同请求换 measurement 为 sim_itest：
{"code":0,...写入成功}
$ curl -s -u root:taosdata -d "SELECT * FROM gateway.sim_itest" http://127.0.0.1:16041/rest/sql
{"code":0,...,"data":[["2026-10-07T08:33:20.000Z",24.5,42.5,"sim-itest","default","sim_itest_default"]],"rows":1}
```

measurement 直接取 `${node_name}`（lib.rs:405-406）未做表名消毒（子表名 gateway_table 有 `sanitize_table_name`，超表名没有）；且 taosAdapter 行协议错误返回 HTTP 200 + JSON code，`send_lines` 只看 HTTP 状态（lib.rs:625-650）→ 即使修复缺陷①，含 `-` 的节点名写入仍会被静默丢弃并计为「已送达」。

**现象 C（缺陷①）**：nb-td 节点 `{"connected":false,"queue_len":165→367,...}`，无任何写入到达。

**结论**：**未通过**。三层问题叠加：数据发不出（①）→ SQL 调用格式错误（②）→ 即使发出、measurement 合法性也不保证且错误被吞（③）。

### 4.5 plugin-kafka ↔ apache/kafka:3.9.0 —— ⛔ 未覆盖（插件不可加载）

**容器**：`iotgw-itest-kafka`（apache/kafka:3.9.0，KRaft 单节点，advertised `localhost:19092`）。

**Broker 本身验证可用**（容器内 CLI 环回）：

```console
$ docker exec iotgw-itest-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:29092 --create --topic itest-broker-probe
Created topic itest-broker-probe.
$ echo probe-msg-2026-10-07 | kafka-console-producer.sh ... && kafka-console-consumer.sh --from-beginning --timeout-ms 8000
probe-msg-2026-10-07
```

**插件侧不可加载，证据链**：

1. **builtin 未注册**：`gateway/gateway-server/src/main.rs:81-86` 注释「北向（kafka 不进 builtin：需要 librdkafka C 库，仅 .so 部署）」，静态注册仅 mqtt/http/influxdb/tdengine。实例 B 的 `GET /api/plugins/north` → `[]`；尝试建节点：

   ```console
   $ POST /api/nodes {"name":"nb-kafka","kind":"north","plugin_name":"kafka","config":{...}}
   {"code":"bad_request","message":"north plugin not found"}   http=400
   ```

2. **FFI 导出缺失**：`cargo build --release -p plugin-kafka --features "ffi,kafka-client"` 可编译通过（VS 自带 CMake `cmake version 4.3.1-msvc1` 成功构建 librdkafka，产物 `target/release/plugin_kafka.dll` 4.36MB），但 `gateway/gateway-plugins/plugin-kafka/src/ffi.rs` 全文只有一行占位注释：

   ```rust
   // FFI bindings placeholder — build with --features ffi to enable
   ```

   网关加载 dll 日志：

   ```console
   WARN gateway_core::loader: load plugin: no south/north symbols found path=...\plugin_kafka.dll
   ```

   （同目录 `plugin_sim.dll` 正常加载：`loaded south .so ... name=sim`，说明宿主 FFI 加载链路本身没问题，是 kafka 插件没有导出符号。）

3. **对照**：plugin-http/influxdb/tdengine 的 ffi.rs 同样是占位符，但它们有 builtin 注册兜底；kafka 两边都缺 → 任何部署形态都不可用。

**结论**：**未覆盖**——按任务对象做真机联调的前提（插件能被网关加载）不成立；需先补 FFI 导出或注册 builtin（涉及产品代码，超出本次联调范围）。环境侧（broker）已验证可用。

### 4.6 plugin-modbus-tcp（南向）↔ oitc/modbus-server —— ✅ 通过

**容器**：`iotgw-itest-modbus-server`（oitc/modbus-server:latest，Modbus TCP 从站，主机 15020→容器 5020，日志 `Starting Modbus Server, v2.3.0`）。

**读链路**：建节点（client 模式，host 127.0.0.1:15020，slave_id 1，默认组/标签 `holding_0` 地址 `4x!0` uint16），启动后 1s 采集周期正常：

```json

{"connected":true,"last_error":null}     // connection-status
```

**写→读回**（经网关 REST 向从站寄存器写值，再等采集周期回读）：


## 5. 缺陷清单（供修复排期）

### 缺陷① 北向 worker 引导死锁（http / influxdb / tdengine / kafka 共有）

**现象**：节点启动后 `connected` 永远为 false，`on_group_data` 产生的数据只进离线队列（`queue_len` 持续增长），服务侧零到达。

**根因**（初始状态 `connected=false, healthy=true`）：

- `on_group_data`：`if !connected { enqueue; return; }` —— 数据不走 mpsc 通道：
  - plugin-http/src/lib.rs:360-364
  - plugin-influxdb/src/lib.rs:411-415
  - plugin-tdengine/src/lib.rs:462-466
  - plugin-kafka/src/lib.rs:369-374
- worker 的 `connected` 只在一条记录**发送成功**后置 true（http:452 / influxdb:546 / tdengine:609 / kafka:490），而 worker 的记录唯一来源是 mpsc `record_rx`（http:433 等）→ 通道里永远不会有记录；
- 离线队列补发分支 `_ = sleep(backoff), if !healthy` 因初始 `healthy=true`（http:425/478 等）被禁用 → 队列也无人消费。

闭环死锁：**首条消息永远发不出**。

**对照（mqtt 为何正常）**：plugin-mqtt 的连接建立在 `run_event_loop` 的 `eventloop.poll()` 中（plugin-mqtt/src/lib.rs:475-485），ConnAck 到达即置 `connected=true`，与数据通道无关；publish 也直接走 rumqttc client。

**单测未覆盖**：`cargo test -p plugin-http -p plugin-influxdb -p plugin-tdengine -p plugin-kafka -p plugin-mqtt -p gateway-plugin-common` 全绿（31+19+10+20 通过）——现有单测只覆盖格式化/分类/队列数据结构，未覆盖「真连接后的首条投递」。

**修复方向**（供参考）：worker 启动时先做一次连通性探测/首条队列投递，或 `on_group_data` 在未连接时也把记录交给 worker（worker 统一负责入队/发送与重试）。

### 缺陷② plugin-tdengine 对 taosAdapter `/rest/sql` 使用 JSON 信封体

- 位置：plugin-tdengine/src/lib.rs:204-208（建库）、:239-244（版本探活）；
- taosAdapter（TDengine 3.x）期望裸 SQL 字符串体；实测回 `{"code":9728,"desc":"unrecognized token: ..."`（HTTP 200）；
- 连带问题：响应只检查 HTTP 状态码（:211-213 与 send_lines :625-650），SQL 级错误被当成成功——日志出现假阳性 `tdengine database 'gateway' ensured`，而服务端 `SHOW gateway.STABLES` 实为 Database not exist。

### 缺陷③ plugin-tdengine measurement 未做表名消毒 + 行协议错误被静默吞掉

- measurement 直接用 `${node_name}`（lib.rs:405-406），节点名含 `-`（如本次 `sim-itest`）→ taosAdapter 行协议语法错误 9728；子表名（gateway_table）有 `sanitize_table_name`，超表名没有；
- 行协议端点错误同样是 HTTP 200 + JSON code，`send_lines` 只看 HTTP 状态 → 修复缺陷①后仍会把写入失败计为已送达。

### 缺陷④ plugin-kafka 无法以任何形态被网关加载

- builtin 未注册（gateway/gateway-server/src/main.rs:81-86，注释明示「仅 .so 部署」）；
- `ffi.rs` 为占位符（plugin-kafka/src/ffi.rs 全文 1 行注释），cdylib 无导出符号，宿主加载报 `no south/north symbols found`；
- 对照组：plugin-sim.dll（真实 `gateway_sdk::export_south_plugin!` 导出）在同一宿主加载成功。
- 影响：联调对象 5 无法进行真机验证；broker 侧环境已验证可用（§4.5）。

### 其他（次要，顺带发现）

- plugin-http `on_group_data` 硬编码 `payload_for_format(&data, DEFAULT_UPLOAD_FORMAT)`（plugin-http/src/lib.rs:352），节点配置的 `upload_format` 不生效；
- plugin-kafka `on_group_data` 硬编码主题模板 `"gateway/data/${node_id}/${group_id}"`（plugin-kafka/src/lib.rs:356），节点配置的 `topic_template` 在该路径不生效；
- 北向离线队列目录默认值是 **CWD 相对路径**（如 `data/http-queue`，plugin-http/src/lib.rs:36 及各插件同名常量），不随 `GATEWAY_DATA_DIR` 走：本次网关以仓库根为 CWD 原生运行，队列文件落在了 `<repo>/data/http-queue|influxdb-queue|tdengine-queue`（容器部署时 WORKDIR=/app 恰好与 /app/data 对齐，故容器形态未暴露）。原生自定义数据目录部署时需逐节点显式配置 `cache_dir`。

### 7.7 新发现缺陷⑤（供下批修复排期）：行协议字段分隔符 `", "` 含空格

- **位置**：gateway/gateway-plugin-common/src/line.rs:117（`encode()` 字段循环 `out.push_str(", ")`）；plugin-influxdb 与 plugin-tdengine 共用该编码器（两插件 `use gateway_plugin_common::line::{..., encode, ...}`）；
- **影响**：InfluxDB 返回 400 `invalid field format`（→ `dropped_rejected` 静默丢弃）；taosAdapter 返回 500 `[0x127] invalid timestamp:...`（→ 无限重试，离线队列持续增长）——**缺陷①②③修复后北向 influx/tdengine 数据仍到不了库**；
- **佐证**：line.rs 单测只断言转义/整型后缀，无分隔符断言（全绿但线上格式错误）；上一轮被缺陷①掩盖（数据从未发出）；
- **修复方向**：line.rs:117 `", "` → `","`，并补一条「多字段编码分隔符为 `,` 无空格」的单测（与官方行协议语法对齐）。
