### 6.5 `bench` — 限并发调度器评估（Q5 规模复测与决策）

**提交**：`4215a48`

决策：**暂不需要实现「共享 interval 的限并发调度器」**——评估决策项，本批未做任何实现；数据、推理与 5 条复评触发条件见 `docs/design/调度器评估-2026-10-07.md`。依据：① `优化方案总览` §15.2 的前提已过时——调度器已是每运行中南向节点一个 task + 固定节拍 + 全局信号量 32（manager.rs:991-1146，`GATEWAY_MAX_CONCURRENT_POLLS` 可调）；② Q5 两次背靠背 bench（release，200 节点 × 50 点位）波动 ≤1%（总线发布 214,685/215,248 msg/s、端到端 212,079/213,352、扇出 217,881/237,000；持久化保存 73,940/82,231 µs，±11%），与 10-06 Q5 基线同量级；③ 形态等价微实验（复刻 manager.rs:1050-1146，运行后已删）：200 调度 task 内存增量 ≈ 0.6 MB（≈3 KB/task）、Q5 基准形态零超限、唤醒仅 200 次/s；④ 附带正交发现：本机 Windows 下 tokio 1.49.0 sleep 量化到 15.6ms（开 `timeBeginPeriod(1)` 后同架构跑满 2300 polls/s、稳态零超限）——千级组饱和由计时器量化而非 task 架构造成，计时器分辨率修复建议作为独立小项拍板。共享 interval 调度器对内存/调度开销/节拍精度三个维度均无可测收益，反增动态变组与取消语义复杂度。bench 输出写 %TEMP%（未动 `docs/bench/` 既有基线）。
