## 2. 可靠性风险清单

> 分级定义：**P0** = 上线前必须修复（安全/数据丢失/进程崩溃）；**P1** = 版本内必须修复；**P2** = 规划修复。
> 每条给出：场景 → 预期行为 → 风险 → 建议验证方式。无法静态确认的标注「**待核实**」。

### 2.1 P0

#### P0-1 仓库内置配置默认关闭 API 认证（`disable_auth: true`）

- **场景**：使用仓库内 `config/gateway.json` 启动网关（`Config::from_env()` 在无 `GATEWAY_CONFIG` 时读取该文件）。
- **预期行为**：默认应对所有管理类 API 强制认证。
- **风险**：`config/gateway.json` 内容为 `{"port": 4000, ..., "disable_auth": true, "token": null, ...}`；`auth_middleware` 在 `state.config.disable_auth == true` 时**直接 `next.run()`**，全部 API（含 `/api/nodes`、`/api/nodes/:id/write_tags`、`/api/users`、`/api/restore`、`/api/backup`）**完全匿名可访问**。攻击者可：读取/篡改全部设备配置、下发写值反控现场设备、创建管理员账号、下载含明文凭据的备份。`main.rs:133` 还绑定 `0.0.0.0`，默认对外暴露。
- **建议验证方式**：
  1. 集成测试：以仓库默认配置启动 `axum::serve`（`TcpListener::bind("127.0.0.1:0")`），不带 `Authorization` 头请求 `GET /api/nodes` 与 `POST /api/nodes/:id/write_tags`，断言 **401**；
  2. 反向用例：不带认证访问 `/api/health`、`/api/version` 断言 200；
  3. 加一条"配置守卫"测试：断言仓库 `config/gateway.json` 的 `disable_auth` 为 `false`（防止再次被误提交）。

#### P0-2 默认管理员弱口令硬编码且自动创建

- **场景**：`UserStore::open()` 首次打开数据库时（`users/store.rs:129-145`）。
- **预期行为**：首次启动应强制设置强口令，或使用随机初始口令并打印一次。
- **风险**：`const DEFAULT_ADMIN_PASSWORD: &str = "admin123";` + `DEFAULT_ADMIN_USERNAME = "admin"`；代码在 admin 不存在时**自动插入该弱口令账号**（仅日志提示"please change password"）。任何人可 `admin/admin123` 登录获取管理员权限。另有 `GATEWAY_RESET_ADMIN_PASSWORD=1` 环境变量可将口令重置为弱口令。
- **建议验证方式**：
  1. 单测：临时目录 `UserStore::open(temp_db)` → 断言 `login("admin","admin123")` 的行为符合"设计决策"（要么拒绝、要么强制改密）；
  2. 集成测试：断言首次启动后 `/api/users` 列表存在 admin，且用默认口令登录**必须被拒绝或强制跳转改密**；
  3. 静态检查：CI 增加 `grep -R "admin123" gateway/` 失败即阻断。

#### P0-3 备份加密密钥硬编码且 KDF 过弱

- **场景**：`POST /api/backup` 导出快照（`backup.rs`）。
- **预期行为**：备份密文应只能由持有高强度密钥者解密。
- **风险**：
  1. `config.rs:62-66` 默认密钥为**硬编码字符串** `gateway-backup-default-secret-change-in-production`，且已随仓库 `config/gateway.json` 提交；任何人拿到备份文件 + 开源代码即可解密，备份内的**设备地址表、MQTT 用户名/口令、全部点位配置**全部泄露；
  2. `derive_key()` 仅对密钥做**单轮 SHA-256**（无 salt、无 PBKDF2/argon2/scrypt），口令类密钥可被彩虹表/低成本暴力破解（项目本身已依赖 `argon2`，却未用于此处）；
  3. `restore` 处理函数在 `password` 字段为空时**回落到默认密钥** `DEFAULT_BACKUP_SECRET`，即"空口令也能解密"。
- **建议验证方式**：
  1. 单测：`encrypt_backup → decrypt_backup` 往返一致；篡改 1 字节断言 `decrypt_backup` 返回 Err（GCM tag 校验）；
  2. 安全用例：断言默认密钥路径在启动时**打印 ERROR 告警**（或启动失败），且空 `password` 不得回落默认密钥；
  3. 用例：用默认密钥能解密他人备份 → 该用例应失败并驱动修复。

#### P0-4 FFI 阻塞调用未在 `spawn_blocking` 中执行（文档与实现不符）

- **场景**：以 `.so/.dll` 方式加载插件（`PluginLoader::load`）后，`SouthSoAdapter`/`NorthSoAdapter` 的每个 trait 方法。
- **预期行为**：插件内为 `block_on`（见 `plugin-sim/src/ffi.rs:9-15` 等），宿主应在 `spawn_blocking` 中执行，避免占满 tokio 工作线程。
- **风险**：
  1. `loader.rs:67-68` 注释明确写"阻塞调用在 `spawn_blocking` 中执行"，但 `run_sync()`（loader.rs:95-101、389-395）**实现为直接 `f(self.handle)` 同步调用**，注释与实现不符；
  2. 插件侧 `block_on` 会在当前线程**新建 tokio current_thread runtime 并阻塞**——该调用发生在宿主 tokio 工作线程上，存在 `Cannot start a runtime from within a runtime` panic 的可能（**待核实**：需实测确认 tokio 1.x 在此场景是否 panic）；
  3. 一旦 panic 穿越 `extern "C"` 边界（非 `C-unwind`），Rust 1.71+ 会直接 **abort 整个网关进程**；
  4. 即使不 panic，Modbus/OPC UA 等慢设备会把宿主工作线程**长时间阻塞**，导致所有节点停摆（tokio 默认工作线程数 = CPU 核数）。
- **建议验证方式**：
  1. 契约测试：构造一个"故意慢/故意 panic"的测试用 `.so`，断言宿主返回 `Err` 且**进程不退出**、其他节点仍在采集；
  2. 断言 `run_sync` 前后 `tokio::runtime::Handle::current().runtime_flavor()` 非工作线程（或在实现改为 `spawn_blocking` 后用 `tokio::task::block_in_place` 检测）；
  3. 压力场景：单个南向节点 1s 阻塞 × N 个组，断言其他节点的 `south_published` 计数仍在增长。

### 2.2 P1

#### P1-1 消息总线无背压、慢北向静默丢数据且无法定位

- **场景**：南向高频采集 + 北向 MQTT 因网络拥塞消费变慢。
- **预期行为**：背压应传导到生产者（降速）或至少按节点产生可告警的丢包指标。
- **风险**：
  1. `Bus` 使用 `tokio::sync::broadcast`（`bus.rs:35`），`send()` **永不阻塞**；慢消费者直接被跳过，只返回 `Lagged(n)`；
  2. `metrics.north_lagged` 是**全局聚合计数**（`data_flow.rs:46`），`/api/data-flow` **无法区分是哪个北向节点在丢**；丢包仅靠 `warn!` 日志，无阈值告警、无 `/api/metrics` 暴露（**待核实**：`metrics` handler 是否包含 lagged 指标）；
  3. 慢节点长期丢数据时，运维看到的现象只是"数据偶尔缺"，排障成本极高；
  4. `publish` 在无订阅者时返回 `Err`，仅累加 `bus_no_subscribers`，同样无告警。
- **建议验证方式**：
  1. 集成测试：`Bus::with_capacity(4)`，生产者连发 20 条、消费者不 recv → 断言 `recv()` 返回 `Lagged(16)` 且 `metrics.north_lagged == 16`；
  2. 用例：北向节点 A 慢、B 快 → 断言 `/api/data-flow`（或新增字段）能区分 A 的 lagged 数；
  3. 压测：见 §4.3 方案，量化"丢包率 vs 生产速率"曲线。

#### P1-2 节点启停竞态 → 孤儿采集/消费任务

- **场景**：并发调用 `POST /nodes/:id/start` 与 `/nodes/:id/stop`（前端重复点击、脚本重试）。
- **预期行为**：无论调用顺序如何，最终应与节点状态一致，且不留残留任务。
- **风险**：`node_stop`（manager.rs:463）先 `c.remove(&id)` 再 `send()`；`node_start`（manager.rs:303）在 `plugin.start()` 之后才 `c.insert(id, tx)`。若交错为「stop 的 remove 发生在 start 的 insert 之前」，则 start 写入的 `tx` **无人取消**，对应轮询/消费任务**永久运行**：南向持续采集发布、北向持续重复上报（重复数据），且 `node_stop` 再次调用也拿不到该 tx。同理 `set_north_subscriptions`（manager.rs:227-238）与 `node_stop` 之间存在同一竞态窗口。
- **建议验证方式**：
  1. 集成测试（确定性注入）：mock 插件的 `start()` 内 `tokio::time::sleep(100ms)`，在 sleep 期间并发调用 `stop()`，断言结束后轮询任务已退出（`south_published` 计数在 1s 内不再增长）；
  2. 属性测试：随机交织 start/stop/remove 序列，断言最终 `north_cancel`/`south_cancel` map 中任务数与节点状态一致；
  3. 断言重复 `node_start` 不会使 `south_published` 增速翻倍。

#### P1-3 恢复/导入快照不停止既有任务，且绕过 License 门禁

- **场景**：`POST /api/restore` 或启动时 `apply_snapshot`（main.rs:87）。
- **预期行为**：恢复前应先停止所有运行中的节点任务，并对快照内容做 License 校验。
- **风险**：
  1. `restore` handler（handlers.rs:549）直接 `apply_snapshot` → 该流程 `store.clear()` 后**不取消北向消费任务**（北向任务不依赖 Store），再对 Running 节点 `node_start` → 新旧北向任务短暂并存，**重复上报**；
  2. 对南向：旧轮询任务在 `store.clear()` 后检查 `store.group_get(id, gid)` 为 None 会 break，但若新快照含同一 `(node_id, group_id)`，旧任务会在下一个周期重新看到该组并**继续轮询**，与新任务并存 → **双倍采集频率 + 重复数据**（取决于取消信号到达时序，属竞态）；
  3. `apply_snapshot` 的自动启动**不检查 `can_use_plugin`**，而 `main.rs` 中 `apply_snapshot`（第 87 行）发生在 License 加载（第 97 行）**之前** → 未授权插件的节点可在启动时被自动拉起；`restore` 路径同样**不检查 `check_tag_limit`** → 可绕过点位上限。
- **建议验证方式**：
  1. 集成测试：创建运行中的南向+北向节点 → `restore` 一份等价快照 → 断言 `nodes_running` 数量正确、单位时间发布次数未翻倍、无重复 MQTT 消息（用 mock broker 计数）；
  2. 用例：无 license 时导入含付费插件节点的快照 → 断言节点状态为 Stopped 且返回明确错误；
  3. 用例：导入超出 `max_tags` 的快照 → 断言被拒绝。

#### P1-4 MQTT 北向离线缓存：内存态、静默丢弃、顺序与重复

- **场景**：Broker 断线期间持续采集，恢复后补发。
- **预期行为**：断网期间数据应按配置容量缓存（可持久化更佳），恢复后按序补发，并对"缓存溢出丢弃"有明确计数/告警。
- **风险**：
  1. 缓存为**进程内 `VecDeque`**（`plugin-mqtt/src/lib.rs:135`），网关重启/崩溃/插件重载即**全部丢失**——文档（`docs/功能总结与待完善列表.md`）称"离线缓存与恢复补发 ✅ 已实现"，但未说明是纯内存，**文档与实现存在表述落差**；
  2. 溢出时 `if cache.len() < cache_max { push_back } else { /* 静默丢弃 */ }`（lib.rs:302-305）—**无计数、无日志**，`data-flow` 指标中也无"缓存丢弃"项；
  3. 补发仅在收到 `ConnAck` 时触发（lib.rs:361-377）；补发循环与新数据 `publish` **并发**执行 → **乱序**；补发中若 `publish` 失败则 `push_front` 后 `break`，该条可能已在网络上部分发出 → **重复**；
  4. 断线重连为固定 `sleep(5s)`，**无指数退避/抖动**，多节点同时重连会形成重连风暴。
- **建议验证方式**：
  1. 单测（注入 mock client）：`on_group_data` 在 publish 失败时入队；队列满时断言"丢弃计数 +1"（需先补埋点）；
  2. 集成测试：mock broker（可用 `rumqttc` 起本地 broker 或 TCP 假服务）断开 → 采集 N 条 → 重连 → 断言 broker 收到 N 条且**顺序与 ts 单调**；
  3. 故障注入：`kill -9` 网关后重启 → 断言缓存丢失行为符合设计决策（若决策为"可丢失"则应写入文档）。

#### P1-5 FFI 无 ABI 版本校验、无 `catch_unwind`、加载失败处理不完整

- **场景**：`plugins/` 目录放入旧版本/第三方/损坏的 `.so`。
- **预期行为**：宿主应校验 ABI 版本，拒绝不匹配插件；插件内部 panic 应被隔离为 `Err`，不得终止宿主。
- **风险**：
  1. `gateway-sdk/src/ffi.rs` 只定义符号名常量（70-108 行），**不存在 ABI 版本号常量或 `gateway_plugin_abi_version` 符号**；`try_south`/`try_north` 仅靠"符号能否取到"判断，**结构体/语义变更无法被检出** → 版本不匹配时表现为内存破坏或返回乱码；
  2. 所有 FFI 调用无 `std::panic::catch_unwind` 包裹 → 插件 panic 直接跨 `extern "C"` → **进程 abort**；
  3. `load_one` 失败仅 `warn!` 后继续（loader.rs:617），**不影响启动**——行为本身可接受，但无"插件加载失败"的健康位暴露给 `/api/health`；
  4. `SouthSoAdapter::meta()` 中大量 `Box::leak`（loader.rs:122-144）→ 每次构造 meta 都永久泄漏字符串（量级受限，P2）。
- **建议验证方式**：
  1. 契约测试：构造"缺少 `gateway_south_plugin_poll_group` 符号"的 `.so` → 断言 `PluginLoader::load` 返回空注册且不 panic；
  2. 契约测试：构造 `create()` 返回 null 的 `.so` → 断言返回 Err；
  3. 契约测试：构造 `poll_group` 内 `panic!` 的 `.so` → 断言宿主收到 Err 且进程存活（需先加 `catch_unwind`）；
  4. 建议引入 `ABI_VERSION` 常量并增加"版本不匹配 → 拒绝加载"用例。

#### P1-6 SQLite 未启用 WAL/busy_timeout，全量重写式保存

- **场景**：高频配置变更（`state.persist()` 在 handlers 中有 **16 处**调用）与启动加载并发。
- **预期行为**：并发写入应排队成功，读写互不阻塞，崩溃后可恢复到一致状态。
- **风险**：
  1. 全仓库 `grep -i "pragma|journal_mode|busy_timeout|WAL"` → **0 命中**：未启用 WAL、未设置 `busy_timeout`、未设置 `synchronous`；而 `persist.rs:3-5` 文档声称"单文件、支持事务与并发读"——**文档表述缺少实现支撑**；
  2. 每次 `save` 都 `DELETE FROM` 四张表后全量 `INSERT`（persist.rs:352-415），`O(配置规模)`；点位上万时单次保存毫秒级→百毫秒级，且**每次都重写整个文件**；
  3. `save` 每次**新建连接**（spawn_blocking 内 `Connection::open`），并发 `persist()` 时两个写事务相遇将返回 `SQLITE_BUSY`（rusqlite 默认 busy_timeout 值**待核实**），表现为"配置保存偶发失败且只在日志里一条 warn"——`state.persist()` 吞掉错误，**调用方 API 仍返回 200**，用户以为保存成功；
  4. 备份仅 `data.db.bak` **单代**，且保存后即被下一次保存覆盖；若损坏发生在"写入→发现"之间，唯一备份可能已被污染；
  5. `persist.rs:444` `path.file_name().unwrap()` 存在 panic 分支（实际不可达，P2）。
- **建议验证方式**：
  1. 集成测试：并发 20 次 `persist()`（不同 tag 变更）→ 断言全部成功且最终 DB 内容与内存一致；
  2. 崩溃恢复测试：写入过程中 `kill -9` → 重启后 `load()` 成功且数据为上一完整版本（或回滚为空），**不得**返回半写数据；
  3. 用例：save 失败时 `AppState::persist` 应让 API 返回 5xx（当前吞错）；
  4. 大配置压测：1 万点位下测量单次 `save` 耗时，作为基线。

#### P1-7 节点插件配置修改（`node_setting`）不做 schema 校验

- **场景**：`PUT /api/nodes/:id/setting` 提交任意 JSON。
- **预期行为**：应与 `node_create` 一样用插件 `config_schema()` 校验。
- **风险**：`validate_config` 全仓库仅在 `manager.rs:125/131`（`node_create`）被调用两处；`node_setting`（manager.rs:773-798）**直接把 config 交给插件**，非法配置可落盘并生效（如 port 为字符串、host 为空），可能触发插件内部 panic 或静默降级。
- **建议验证方式**：单测——mock 插件的 schema 要求 `port` 为 1-65535 整数，`node_setting` 传入 `{"port": 99999}` 应返回 Err 且不写 Store。

#### P1-8 静态资源目录穿越风险（待核实）

- **场景**：`serve_static_or_index`（api/mod.rs:121-172）用 `base.join(uri.path())` 拼接。
- **预期行为**：任何请求都不得读到 `static_dir` 之外的文件。
- **风险**：`http::Uri` 不做路径规范化，形如 `/../../etc/passwd` 的请求路径经 `Path::join` 后可能逃逸到 `web/dist` 之外；随后 `file.exists() && file.is_file()` 为真则返回文件内容。**待核实**（需用真实请求实测；部分 hyper/axum 版本会在路由层拒绝含 `..` 的路径）。
- **建议验证方式**：集成测试——用 `tower::ServiceExt::oneshot` 直接向 router 发送请求 `GET /%2e%2e/%2e%2e/etc/passwd` 与 `GET /../../etc/passwd`，断言 404 或 `index.html`，**不得**返回 `/etc/passwd` 内容；同时断言含 `..` 的绝对路径文件（如 `/etc/hosts`）不可读。

### 4.3 基准测试与压测方案

**目标 1：验证 4096 总线容量与背压行为**

```
benches/bus_throughput.rs（criterion）
- 参数化：capacity ∈ {64, 1024, 4096}；生产者速率 ∈ {1k, 10k, 50k msg/s}；消费者数 ∈ {1, 4}
- 消费者延迟档位：0ms / 1ms / 10ms（模拟慢北向）
- 输出指标：
  · publish 吞吐（msg/s）与 p50/p99 延迟
  · 丢包率 = north_lagged / south_published
  · 内存占用（RSS 采样，验证 4096 × GroupData 的上界）
- 判据：容量 4096 且消费者延迟 1ms 时，10k msg/s 下的丢包率应 < X%（X 由基线确定后写死为准出门禁）
```

**目标 2：端到端吞吐与丢包率（南向 → 北向）**

```
tests/soak.rs（#[ignore]，CI nightly job 运行）
- 拓扑：N 个 sim 南向节点 × M 个组 × K 个 tag，采集间隔 100ms；1 个 MQTT 北向订阅全部
- mock broker：本地 rumqttc broker 或 TCP sink，仅计数不落盘
- 运行 30 分钟，每 10s 采样 /api/data-flow
- 断言：
  · north_forwarded / south_published ≥ 99.9%（无故障时）
  · north_lagged == 0（无故障时）
  · RSS 增长 < 10%（无内存泄漏）
  · 打开 FD 数稳定（无连接泄漏）
```

**目标 3：故障注入下的韧性**

| 故障 | 注入方式 | 断言 |
|---|---|---|
| 南向设备断线 | FakeSouthPlugin 按脚本返回 Err | 节点 `connection_status.connected=false`；`south_published` 停止；恢复后自动继续，无需重启 |
| MQTT broker 不可达 | 关闭 mock broker / toxiproxy | 消息进入缓存；`connection_status.connected=false`；恢复后补发条数 == 缓存条数（未溢出时） |
| 插件崩溃 | fixture `.so` 内 panic / `abort` | 宿主存活；该节点置为 Error；其他节点不受影响 |
| 磁盘满 | `data_dir` 指向满的小 tmpfs | `persist()` 失败时 API 返回 5xx 且日志有 ERROR（**当前行为：吞错返回 200 → 需先修**） |
| 慢北向 | 消费者 sleep 50ms | 丢包率与 `Lagged` 计数符合容量推算值，且有告警 |
