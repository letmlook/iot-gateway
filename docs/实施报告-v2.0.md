### 1.2 `console-api-surface` — 管理台 API 面 P0（计划外发现）

**发现过程**：T2 接线后按「后端如何挂载 history 路由」追代码，发现前端 `BASE='/api/v1'` 与后端路由表对不上，随即起本地网关实证。

**实证（release 路由等价的 debug 构建）**：

```
GET  /api/v1/health          → 404      GET  /api/health          → 200
POST /api/v1/auth/login      → 404      POST /api/auth/login      → 200
GET  /api/v1/plugins/south   → 404      GET  /api/plugins/south   → 200
GET  /api/v1/nodes           → 200      （6 个分页端点的 v1 别名存在）
```

**根因**：`887d387`（2026-10-06「API v1 前缀」批）把前端 `BASE` 改为 `/api/v1`，但后端同批只为 **6 个分页端点**（users / nodes / nodes/:id/groups / nodes/:id/tags / nodes/:id/values / rules 的 GET）注册了 `/v1` 别名；auth / plugins / license / tenants / backup / history 等按路由表注释「**不过 v1 别名**」只存在于 `/api` 裸路径。自此管理台登录、插件、授权、租户、备份、系统配置等页面全部 404——节点/标签/用户页因恰有别名而「看起来正常」，缺陷得以潜伏。另外分页端点返回 `Page<T>`（{items,total,page}），而前端消费方按 legacy 形状（数组 / `{users:[...]}`）编写（`gateway.js` 直接 `.filter`、`Users.vue` 取 `res?.users`），即便别名可达也不兼容——前端整体应走 legacy 面。

**修复（前端单点）**：`web/src/api.js` `BASE` `/api/v1` → `/api`（附契约注释）；`gatewayWs.js` 的 `/api/v1/ws` 不动（`/v1/ws` 有别名注册，WS 一直正常）。

**回归防护**：`gateway-server/src/api/mod.rs` 新增 `console_api_surface_reachable_at_bare_api_prefix`——覆盖管理台调用的各路由族（/api 裸路径不得 404），并锁定对照组契约（`/v1/plugins/south`、`/v1/auth/login` 404 是既定契约；`/v1/nodes` 别名存在）。

**门禁**：`cargo test -p gateway-server` → **62 lib + 63 bin + 5 ws 全绿**；`cargo fmt --check` / `cargo clippy --lib --tests -D warnings` 无告警；`npm run build` + `tsc` ✅；本地起网关（挂新 dist）按修复后真实调用路径 curl 全矩阵通过。

**记录出入（如实注明）**：`7daa16b`（2026-10-25）提交信息称 backup/restore 修复前报 401——与本发现（`/api/v1/backup` 404）不符；推测当时验证所用 dist 为 `887d387` 之前的旧构建（BASE 仍为 `/api`）。该批的代码修复本身（补凭据、401 跳转）仍然正确且必要。**教训**：管理台自 `887d387` 起未做过端到端手工验收，文档验收声明需附可复现路径——与本仓库既有工程教训一致。

**遗留**：本机无 GUI 浏览器，管理台 + 历史页的端到端浏览器冒烟仍未做（API 面已全部实证可达）；建议下次真机联调时补登录 → 各页巡检 → 历史曲线查询的人工验收清单。

### 3.1 本机环境已知问题（非本批引入，如实记录）

worktree 复现相同段错误 → 与本批无关；CI 的 Ubuntu（较旧 glibc）同测试持续绿。初步判断为
glibc 2.43 的 dlopen/dlclose 与 C-unwind panic 的交互问题，待专项根因（gdb + 最小复现），
不阻塞本批；恢复手段：在 glibc ≤2.39 环境（CI 或容器）运行该测试。
