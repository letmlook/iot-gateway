### 1.2 `console-api-surface` — 管理台 API 面 P0（计划外发现）

**发现过程**：T2 接线后按「后端如何挂载 history 路由」追代码，发现前端 `BASE='/api/v1'` 与后端路由表对不上，随即起本地网关实证。

**实证（release 路由等价的 debug 构建）**：

```
GET  /api/v1/health          → 404      GET  /api/health          → 200
POST /api/v1/auth/login      → 404      POST /api/auth/login      → 200
GET  /api/v1/plugins/south   → 404      GET  /api/plugins/south   → 200
GET  /api/v1/nodes           → 200      （6 个分页端点的 v1 别名存在）
```

**根因**：`887d387`（2026-10-06「API v1 前缀」批）把前端 `BASE` 改为 `/api/v1`，但后端同批只为 **6 个分页端点**（users / nodes / nodes/:id/groups / nodes/:id/tags / nodes/:id/values / rules 的 GET）注册了 `/v1` 别名；auth / plugins / license / tenants / backup / history 等按路由表注释「**不过 v1 别名**」只存在于 `/api` 裸路径。自此管理台登录、插件、授权、租户、备份、系统配置等页面全部 404——节点/标签/用户页因恰有别名而「看起来正常」，缺陷得以潜伏。另外分页端点返回 `Page<T>`（{items,total,page}），而前端消费方按 legacy 形状（数组 / `{users:[...]}`）编写（`gateway.js` 直接 `.filter`、`Users.vue` 取 `res?.users`），即便别名可达也不兼容——前端整体应走 legacy 面。

**修复（前端单点）**：`web/src/api.js` `BASE` `/api/v1` → `/api`（附契约注释）；`gatewayWs.js` 的 `/api/v1/ws` 不动（`/v1/ws` 有别名注册，WS 一直正常）。

**回归防护**：`gateway-server/src/api/mod.rs` 新增 `console_api_surface_reachable_at_bare_api_prefix`——覆盖管理台调用的各路由族（/api 裸路径不得 404），并锁定对照组契约（`/v1/plugins/south`、`/v1/auth/login` 404 是既定契约；`/v1/nodes` 别名存在）。

**门禁**：`cargo test -p gateway-server` → **62 lib + 63 bin + 5 ws 全绿**；`cargo fmt --check` / `cargo clippy --lib --tests -D warnings` 无告警；`npm run build` + `tsc` ✅；本地起网关（挂新 dist）按修复后真实调用路径 curl 全矩阵通过。

**记录出入（如实注明）**：`7daa16b`（2026-10-25）提交信息称 backup/restore 修复前报 401——与本发现（`/api/v1/backup` 404）不符；推测当时验证所用 dist 为 `887d387` 之前的旧构建（BASE 仍为 `/api`）。该批的代码修复本身（补凭据、401 跳转）仍然正确且必要。**教训**：管理台自 `887d387` 起未做过端到端手工验收，文档验收声明需附可复现路径——与本仓库既有工程教训一致。

**遗留**：本机无 GUI 浏览器，管理台 + 历史页的端到端浏览器冒烟仍未做（API 面已全部实证可达）；建议下次真机联调时补登录 → 各页巡检 → 历史曲线查询的人工验收清单。

### 10.1 方案：告警 → 数据 → 北向（桥接而非平行系统）

- server 侧零改动：alarm 端口 → alarm_to_data 连线天然合法（validate 只查端口名），

### 12.4 T5 soak 长跑框架 + 冒烟

- **[soak.sh](../scripts/soak.sh)**（默认 72h 口径）：
  - 拓扑：sim 南向 ×2（1s/2s 周期）→ kafka stub 北向订阅（stub 丢弃计数累积、无
    离线队列磁盘风险，即「慢消费者」形态，长跑观察 Lagged 语义）+ flow 告警链路
    （threshold_alarm low=100 恒触发 → sink_alarm 持续落库）；
  - 周期演练：每 reconnect-interval（默认 600s）stop/start 南向节点（节点级重连）；
  - 采样：每 interval 记 health / nodes_running / 发布计数 / Lagged（按 node 分解）/
    RSS / 库大小（主文件 + WAL）→ samples.jsonl；
  - 结束摘要 summary.md：RSS 峰值与末值、发布计数、Lagged、告警行数、人工判据。
- **冒烟通过**（150s/60s 采样）：采样 7 次、健康异常 0、发布 63、北向 Lagged 0、
  告警落库 1、RSS 48→29MB 平稳无上扬、SIGTERM 优雅停机。
- 过程发现（脚本错误，非产品缺陷）：初版阈值 `"low":-1` 意为「低于 -1 触发」，sim
  值域 15-25 永不触发——threshold_alarm 的 low 语义是低于下限、high 是超上限，改
  `low=100` 恒触发。经最小复现（独立端口临时实例 + 最小 flow）确认语义正确后修正脚本。
  另：告警行数封顶于「告警键组合数」而非条数——同键 active 告警只前移时间戳不新增
  行（告警生命周期去重，预期行为），判据说明已按此口径写明。
- **72h 首轮**：由本机 `./scripts/soak.sh [--license data/license.dat]` 后台长跑
  （CI job 上限 6h 不适合 72h 口径）；脚本已含 license 安装与 `--skip-build` 复用。

## 13. M3 后补强批次（2026-11-22）：property tests + 发布链路首跑验证

### 13.1 规则/filters property tests（蓝图 T5 剩余项）

`gateway-core` 新增 10 个性质测试。不引入 proptest/quickcheck 依赖：确定性
xorshift 伪随机（固定种子，失败可重现）批量生成输入，对模块头「对外承诺」语义
的不变量逐条断言。

**filters.rs（6 项）**：
- 绝对死区双边界：|Δ| ≤ db 必抑制、> db 必上报（2000 组随机）
- 相对死区双边界：|Δ| 与 pct%·|base| 的两侧判定（base≠0，避开退化语义分支）
- 聚合序不变量：非空样本 min ≤ avg ≤ max、count=len、first/last 对齐、空集 None
- validate_policy 二择一：任意（含非法组合）policy 不 panic，Err 非空（1000 组）
- passthrough 恒等：混合类型（数值/布尔/字符串）输入逐值原序透传
- onChange 守恒：published + suppressed_tags == 输入点位数（每点位恰一个去向），
  suppressed_msgs == 1 ⇔ 本批零输出

**rules.rs（4 项）**：
- 比较运算逻辑自洽（含 NaN/±inf）：Ne ⇔ !Eq、Eq 对称、Ge ⇔ Gt ∨ Eq、
  Le ⇔ Lt ∨ Eq、有限值上 Gt/Lt 互斥且参数交换对称
- advance 边沿触发五不变量（40 轮 × 500 步随机序列，for_ms/clear_ms 随机）：
  每步至多 1 触发、fire_count 单调、触发当步必满足、两次触发之间必有不满足步、
  last_value 跟踪
- for_ms > 0 时零点满足不得立即触发
- value_for_tag 类型分派：按声明 data_type 产出对应 DataValue 变体，整型截断语义、
  未声明回退 float64

gateway-core lib 测试 65 → 75，全绿；fmt / clippy -D warnings 过。

### 13.2 v2.0.0-rc.1 → rc.3 发布链路首次实跑（T4 收口）

### 13.3 bench-nightly 首跑验证与生效路径说明

- 手动 workflow_dispatch 跑通一次：GitHub Actions 链路（构建 → bench → artifact
  存档 → cache）健康。
- **重要发现**：`schedule` 与 `workflow_dispatch` 事件的 workflow 定义固定读取
  **main 分支**的文件——本次 dispatch 实际执行的是 main 上的旧版存档 workflow；
