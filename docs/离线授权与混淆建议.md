# 离线授权与核心校验逻辑混淆建议

## 一、离线授权机制概览

本项目采用**完全离线**的软件授权方案：

1. **硬件绑定**：`gateway-server/src/license/hardware.rs` 采集系统 ID、CPU 核心数、机器名与首块网卡 MAC，经 SHA-256 生成唯一机器码。
2. **授权文件**：`license.dat` 为 JSON，包含 base64 的 payload 与 RSA 签名；payload 含 `machineId`、`expiryDate`、`features`。
3. **验证流程**：启动时读取 `license.dat`，用内置公钥验签，校验机器码与到期时间，无任何网络请求。
4. **功能分级**：`FeatureManager::can_access(feature_name)` 根据授权中的 `features` 控制免费/收费功能。

## 二、核心校验逻辑位置

- **验签与解析**：`gateway-server/src/license/license.rs` 中 `load_and_verify_license`、`verify_signature`、机器码与到期日比较。
- **功能判断**：`gateway-server/src/license/feature.rs` 中 `FeatureManager::can_access`。
- **机器码生成**：`gateway-server/src/license/hardware.rs` 中 `machine_id`。

## 三、简单混淆与加固建议（不改变行为）

以下建议在不影响功能的前提下，提高逆向与篡改成本：

### 1. 公钥与常量

- **公钥**：将 `BUILTIN_PUBLIC_KEY_PEM` 拆成多段字符串，在运行时按顺序拼接，避免单一大块 PEM 出现在二进制中。
- **魔数/常量**：到期日比较、文件名等使用的字符串可经简单 XOR 或查表在运行时还原，避免明文 `"license.dat"`、`"expiry"` 等集中出现。

### 2. 控制流

- **分支**：将“验签通过/失败”“机器码匹配/不匹配”等关键分支用布尔变量或小函数间接调用，避免 `if (payload.machine_id != current)` 这类一目了然的比较。
- **内联**：对 `verify_signature`、机器码比较等短函数使用 `#[inline(never)]`，或放入单独的小模块，增加调用关系复杂度。

### 3. 符号与导出

- **发布构建**：使用 `release` 构建并 strip 符号（`strip = true` 或发布后 `strip` 二进制），避免函数名、模块路径暴露过多逻辑。
- **禁止内联**：对核心校验函数使用 `#[inline(never)]`，减少被“摊平”到调用方后一眼看穿。

### 4. 时间与完整性

- **时间来源**：当前使用 `chrono::Utc::now()` 做到期比较。可考虑将“当前日期”的获取封装到单独函数，并在多处使用，增加对时间逻辑定位的难度（不改变逻辑）。
- **校验顺序**：可先解析 payload 再验签（仅用于展示或日志时需谨慎），或先验签再解析；保持当前“验签 → 解析 → 机器码/到期”顺序即可，避免将敏感判断集中在一处。

### 5. 依赖与构建

- **依赖**：保持 `rsa`、`sha2`、`machineid-rs` 等为常规依赖即可；无需引入额外“混淆库”，以免引入供应链风险。
- **编译优化**：`release` 下默认的 LTO 与 codegen-units=1 会增大分析难度，可保留。

**注意**：以上均为“简单混淆建议”，无法替代安全设计。私钥必须仅保存在管理员侧（如 `scripts/license_private.pem`），不得随软件分发；授权文件与机器码绑定可防止一证多机。
